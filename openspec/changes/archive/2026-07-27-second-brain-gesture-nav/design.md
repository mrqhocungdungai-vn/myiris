## Context

Change #1 (`second-brain-galaxy-view`, archived) shipped the galaxy as a vanilla `3d-force-graph@1.80.0` instance mounted imperatively inside `GalaxyCanvas` (in `src/components/VaultGalaxy.tsx`), sharing the app's single `three@0.181.2`. Today the galaxy is mouse-only: `onNodeClick` opens a node, and `3d-force-graph`'s built-in TrackballControls handle camera drag/zoom from real pointer events. The note reader (`NoteReader` → shared `ReaderCore`) is opened by click and closed by X/Esc; `NoteReader` deliberately passes `hand={null}` into `ReaderCore`, leaving `ReaderCore`'s already-built fist-close / two-open-palms-resize / open-palm-scroll rAF loop dormant for vault notes (it is live for the task `ReaderOverlay`).

The hand pipeline already exists: `useHandControl` (MediaPipe `GestureRecognizer`) publishes semantic `HandState` and, crucially, an every-frame `stateRef` (`liveHandRef` in `App.tsx`) that imperative rAF readers use so charging a dwell timer never forces a React re-render. `App.tsx` already runs three such loops (universal point-and-dwell click, open-palm scroll, fist-orbit/pinch-scale the orb), each gated off while `secondBrainActive` (the galaxy) or `drawingActive` owns the surface — the 2026-07-24 orb-leak bugfix. `App.tsx` also already hoists `galaxyPositionsRef` above `VaultGalaxy` and holds `openNote` state; `openNoteFromGalaxy` already enforces the single-reader invariant by clearing the task reader.

This change adds the gesture layer on top of that finished surface. It is renderer-only: no main-process, IPC, dependency, or persisted-state changes.

## Goals / Non-Goals

**Goals:**
- Open a node hands-free by pointing + 300 ms dwell (the HUD's universal dwell timing), ghost nodes excluded, matching the mouse `onNodeClick` contract exactly.
- Orbit the camera with a closed fist and zoom it with a pinch, while the galaxy is active and no reader is open.
- Light up the note reader's existing gesture bindings (fist-close, two-palm-resize, palm-scroll) for vault notes by feeding `NoteReader` real hand state.
- One authoritative gesture-context map (reader > galaxy > deck) with no binding collisions — derived from one shared, tested resolver rather than a new ad-hoc guard — and no orphaned reader when the galaxy closes by *any* route.
- Keep everything gated on the existing opt-in hand-control toggle; mouse control unchanged and never left disabled.
- Keep a hands-free way *out* of the galaxy, and an action indicator that names the binding that is actually live.
- Put the subtle logic (hit-test, dwell machine, pose partition, camera step) in a pure module with unit tests, matching the repo's existing test seams.

**Non-Goals:**
- No new render features, backdrop changes, data/IPC changes, or new dependencies.
- No changes to the deck's own gesture loops beyond what already gates them off under the galaxy, plus the one control-island exemption D11 requires. In particular the three shipped deck rAF loops are **not** refactored onto D9's resolver in this change (that is deliberate scope-limiting — see D9's known-debt note), and no attempt is made to unify the four loops themselves.
- No generalization of `main-thread-budget`'s per-frame-allocation requirement beyond this capability. It is currently scoped to the orb's `useFrame`, and this change restates the rule locally (D1's scratch vector, D5's no-loop-when-off) rather than widening another capability's requirement mid-change; a follow-up can generalize it to all steady-state renderer rAF loops.
- No per-node hover tooltips-by-gesture, multi-select, or link-following gestures — out of scope.
- No new persisted preference or env flag; if hand control is off the galaxy is mouse-only exactly as change #1 shipped.

## Decisions

### D1 — Node targeting is a screen-space projection hit-test with a front-of-camera guard, not a THREE.Raycaster

Galaxy nodes are WebGL objects, so the existing `document.elementFromPoint` dwell loop cannot see them (and is suppressed under the galaxy anyway). Each frame the gesture loop projects candidate node positions and picks the node nearest the (already-smoothed) hand point within a pixel threshold (start ~48 px, tune). This mirrors the HUD's existing screen-space dwell rather than introducing a `THREE.Raycaster` with its own camera/scene lifecycle, and it reuses the node objects the renderer already owns in `positionsRef`. **Alternative considered:** a real raycaster against `fg.scene()` — rejected as heavier (needs the node meshes, handles occlusion we don't want, and duplicates state the projection path reads for free).

**Front-of-camera guard (H1) — required, not tuning.** `fg.graph2ScreenCoords()` (i.e. `three-render-objects`' `getScreenCoords`) returns only `{x,y}` and does **no visibility test** — a node *behind* the camera still projects to finite in-viewport pixels, so a naïve "nearest node" test would dwell-open a node behind you while orbiting (a false positive the mouse `onNodeClick` raycaster never has). The loop therefore projects each node with a **single hoisted scratch `THREE.Vector3` reused across nodes and frames** (`scratch.set(n.x,n.y,n.z).project(fg.camera())`, M-2 — never `new THREE.Vector3` per node per frame, which is 60·n allocations/sec of steady GC pressure) and **accepts a node only when its projected `z` satisfies `-1 ≤ z ≤ 1`** (in front of the near plane, within far) before mapping the survivors to pixels and picking the nearest. Ghost nodes (`node.ghost`) and nodes without positions yet (`n.x === undefined`, before the first sim tick) are skipped, identical to / consistent with `onNodeClick` and `applyGraph`'s own guard.

The hand point is in window pixels (`useHandControl` uses `window.innerWidth/Height`) while a projected NDC→pixel mapping is canvas-relative; these coincide today only because `.hud-galaxy` is fullscreen at `(0,0)`. Map projected NDC to pixels using the container's `getBoundingClientRect()` (add its `left`/`top` offset) so a future non-fullscreen galaxy layout doesn't silently misalign the hit-test (L2).

### D2 — Dwell reuses the universal 300 ms / leave-and-re-enter contract

Targeting a node for >300 ms fires `onOpenNote(id, title)` once; the target must be left (pointer moves off the node, or the pointing gesture drops) and re-acquired before it can fire again — the same debounce the universal dwell already enforces, so behavior is consistent across the HUD. Dwell only charges while the hand shows `Pointing_Up` (so a fist meant for orbiting never charges an open).

**The dwell state must survive a suspension (L17).** The loop stops while a reader is open (D7) and while Iris sleeps (D5). If the dwell state were cleared on suspend, closing the reader with the hand still pointing at the same node would immediately re-fire and reopen it — an open/close loop the user cannot escape without moving their hand. The state persists across suspensions and is only reset by actually leaving the target.

**Highlight feedback must re-set the accessor (M6).** `3d-force-graph` re-evaluates node accessors only when `graphData()` is set or the accessor is re-assigned — mutating a `targetedIdRef` the accessor closes over will **not** repaint. So on each *change* of the targeted node the loop re-assigns the accessor (`fg.nodeColor(colorForNode)`, with `colorForNode` reading the current target id) to force a material refresh. Drive the highlight through `nodeColor` (a material update), **not** `nodeVal` (re-setting `nodeVal` rebuilds node geometry → flicker/cost). Feedback is required by the spec; the exact visual is an implementation detail, but "a ref the accessor reads" alone is not sufficient and must not be the plan.

**Target changes need hysteresis, because a repaint is O(n) with material churn (M14).** Re-assigning `nodeColor` re-runs `three-forcegraph`'s whole node digest: every node's accessor is evaluated, a `THREE.Color` is allocated, and where the color differs the old material is `dispose()`d and a fresh `MeshLambertMaterial` allocated. Bounding the trigger to "each change of the target" is not enough on its own — in a dense cluster the nearest-node result flips frame to frame, which would mean up to 60 full-graph digests per second with dispose/allocate churn. So a new candidate must **beat the incumbent by a pixel dead-band and hold for a few consecutive frames** before it is committed as the target. This lives in `dwellStep`'s contract (it already owns target transitions), so it is unit-testable rather than something discovered during manual tuning.

### D3 — Camera orbit/zoom is renderer-owned spherical math driving `cameraPosition()`, looking at an explicit center

A closed fist's frame-to-frame point delta maps to azimuth/polar deltas; a pinch's `pinchDistance` maps to orbit radius (gated per D4). Each frame the loop recomputes the camera position on a sphere centered on the graph center and calls `fg.cameraPosition({x,y,z}, center, 0)`. Two corrections over the naïve form:

- **Pass an explicit `lookAt` (M4).** `three-render-objects` treats a falsy `lookAt` as the **world origin** (`{0,0,0}`) and re-applies it every call — so `cameraPosition({x,y,z}, undefined, 0)` would hard-point the camera at origin, not at the graph. The graph centroid is only *near* origin (a centering force pulls toward it, but pinned `fx/fy/fz` nodes and drift move it), so the loop reads the orbit center from a cached `centerRef` rather than recomputing per frame.
- **The center is recomputed lazily on an invalidation flag, NOT at `applyGraph` time (L-A4 → H4).** A gesture loop with no change signal would recompute the centroid over the whole `positionsRef` Map every frame (the O(n) cost R4 bounds), so it needs a trigger — but computing it *inside* `applyGraph` is the one moment the positions don't exist: newly reconciled nodes are spread from the position-free main-process graph (`node.x === undefined`, which is why `applyGraph` already guards on it), and on the first galaxy open `positionsRef` is empty so **every** node is position-less. `cooldownTicks(Infinity)` then lets the simulation move every node for seconds while `applyGraph` is never called again — the center would stay a pre-layout artifact (or the origin fallback) for the whole session, defeating M4's entire point. Instead keep a `centerDirtyRef`: set it in `applyGraph` **and** from `fg.onEngineStop(...)` (public on the pinned instance), and have the loop recompute the centroid at most once per dirty flag. O(n) on layout events, not per frame, and the center reflects the *settled* layout.
- `0 ms` transition = snap, no tween fighting the per-frame writes (verified: no tween object is created at `transitionMs=0`).

We own the math rather than poking `fg.controls()` because `3d-force-graph` types `controls()` as `object` (it is a TrackballControls instance internally) — reaching into its private state is brittle across the pinned version. **Alternative considered:** synthesize pointer events onto the canvas to drive the built-in TrackballControls — rejected as fragile (event geometry, button state) and indirection over a public API. Mouse control is untouched: real drags still reach TrackballControls. **See R1** for the interaction risk this raises (and the re-enable target-sync trap).

### D4 — Delta drive is gesture-partitioned, smoothed, small, clamped, framerate-tolerant

**Zoom is gesture-gated so it never fights dwell (H3).** `pinchDistance` (thumb-tip↔index-tip) is published *every frame regardless of gesture*, and during `Pointing_Up` the thumb moves freely — so an unconditional pinch→radius mapping would dolly the camera while the user is trying to hold a node dwell, sliding the target out from under the point and resetting the debounce. The hand's pose therefore partitions the three drives with no overlap:

- `Pointing_Up` → node-dwell targeting only (no camera motion),
- `Closed_Fist` → orbit only (from the point delta),
- an **explicitly detected pinch** → zoom only,
- anything else (open palm, an unrecognized pose, a hand just resting in frame) → **no drive at all**.

**"Pinch" must be an explicit predicate, not the leftover branch (H3).** MediaPipe's canned classes have no pinch, and `HandState` exposes only a continuous `pinchDistance` — so a partition written as "otherwise → zoom" would let `Open_Palm`, `Victory`, `Thumb_Up` and `None` drive the camera radius, i.e. *a hand resting in frame dollies the view*, and two open palms (the reader-resize gesture) would drive zoom while the indicator says "resize". `galaxy-nav.ts` therefore defines the predicate itself and `driveFor` returns `null` when nothing matches: a single tracked hand, not `openPalm`, with `pinchDistance` below an engage threshold, released above a slightly larger threshold (hysteresis, so a hand hovering at the boundary doesn't chatter between zoom and no-drive). The thresholds are constants in the pure module, so they are tunable and unit-testable.

**Zoom is relative with a seeded reference, not an absolute map (H3).** An absolute `pinchDistance → radius` map contradicts this design's own no-jump rule: there is no reference to seed, so the radius snaps to whatever the current pinch maps to the instant the pose engages. (The orb loop's pinch path is absolute and unseeded, but an orb scale snap is harmless where a camera radius snap is not.) So zoom takes the same shape as orbit: on engage, seed the reference pinch and the current radius; each frame apply the *delta* from that reference, clamped to a min/max distance so the camera can neither invert through the center nor fly off. `radiusStep(radius, pinchDelta, sensitivity, min, max)`.

`useHandControl` already exponentially smooths the primary point. Orbit sensitivity is a small radians-per-pixel constant. A large single-frame jump (hand re-acquired elsewhere, or a pose transition) is ignored via a "first frame after a drive (re)engages seeds the reference, applies no delta" guard — the same shape as the orb loop's `prevFistPoint` seeding, now applied to **both** drives. This keeps the drive stable without a physics/inertia model.

**Seeding must also re-derive from the live camera (M13).** The loop caches a spherical `(radius, phi, theta)`, but a *mouse* drag moves the camera through TrackballControls without touching that cache — so the first gesture frame after a mouse drag would snap the camera back to wherever gesture control last left it. On every drive engage, re-derive the spherical from the live camera (`spherical.setFromVector3(camera.position.clone().sub(center))`) before applying any delta. The `enabled` latch covers gesture → mouse; this covers mouse → gesture.

### D4b — The loop is a thin driver over a pure policy module (`src/lib/galaxy-nav.ts`)

Everything decided in D1–D4 — the hit-test, the pose partition, the spherical step, the pinch clamp — is pure logic with no dependency on React, the DOM, or the live `fg` instance. It goes in **`src/lib/galaxy-nav.ts`**, and `GalaxyCanvas`'s rAF loop becomes a thin driver that feeds it the frame's inputs (H-A3 / M-A4):

- `nearestNodeAt(nodes, camera, rect, point, thresholdPx)` → the targeted node or null. Owns the front-of-camera test and the `getBoundingClientRect` offset. The module owns its scratch `Vector3` at module scope (M12 — pure module, single-threaded, one live galaxy), so the caller never passes one and the M-2 no-allocation guarantee is testable from inside the module's own test. State the test as **accept `-1 ≤ z ≤ 1`**, not "reject `z < -1 || z > 1`" (L15): a point *at* the camera projects to `NaN/NaN/-Infinity` and every NaN comparison is false, so only the accept form rejects it.
- `dwellStep(state, candidate, now, holdMs)` → `{ state, target, fire }` (the 300 ms + leave-and-re-acquire contract, plus M14's dead-band/hold before a new candidate is committed as the target).
- `driveFor(hand)` → `"dwell" | "orbit" | "zoom" | null` (the D4 partition, with an explicit pinch predicate and `null` for everything unmatched).
- `orbitStep(spherical, delta, sensitivity)` and `radiusStep(radius, pinchDelta, sensitivity, min, max)`.

This matches `renderer-structure`'s policy (shared logic under `src/lib/`, components presentational) and the repo's established test seams — `src/lib/hand.ts` + `hand.test.ts` (`semanticEquals` extracted out of `useHandControl` for exactly this reason), `src/lib/downsample.ts`, `src/lib/tasks.ts`, and change #1's own `electron/vault-graph-parse.mjs` + test. It also makes the highest-risk corrections in this design **headlessly testable**: a `THREE.PerspectiveCamera` + `updateMatrixWorld()` needs no WebGL context, so "one node in front, one behind → only the front one is returned" is a real unit test rather than a webcam wave. Without this seam, every guard in D1–D4 would be verifiable only by hand (tasks 9.2–9.4), which is why change #1 extracted its parser the same way. Dependency direction: component → (loop) → pure policy → nothing.

### D5 — The gesture loop lives inside `GalaxyCanvas`, reading the hoisted hand ref

The `fg` instance is encapsulated in `GalaxyCanvas`; the camera/projection work needs it, so the rAF *driver* belongs there (the *policy* it calls does not — D4b) — exactly as `ReaderCore` owns its own gesture rAF loop against the `fg`-free reader DOM. The props thread `App.tsx` → `HudShell` → `VaultGalaxy` → `GalaxyCanvas` (App renders `HudShell`, which renders `VaultGalaxy` — there is no direct App→VaultGalaxy edge, so `HudShell`'s prop surface must be extended, M1): `liveHandRef` (per-frame, not React state), `handControl`, and a derived `readerOpen` (`openNote != null || expandedTaskId != null`, L1). `running` is already a prop on `GalaxyCanvas` (it pauses the render loop on HUD sleep, `pauseAnimation()`).

**The loop must respect the render's pause and not spin when off (H-1 / M-1).** `webPreferences.backgroundThrottling` is `false`, so Chromium never throttles rAF when the window is occluded or blurred — every loop must self-gate. The galaxy render loop already pauses on `!running` (which tracks Iris being **asleep**, deliberately not window blur — the orb keeps rendering while awake but unfocused, and the galaxy follows the same signal); the gesture loop must do the same, or it will project all nodes + drive the camera at 60 fps while the galaxy is frozen asleep — a battery/fan regression on a floating always-on-top HUD, and a *correctness* bug: mutating `cameraPosition()` while `pauseAnimation()` holds the render means the camera silently orbits/dollies during sleep and snaps on wake. So:

- The gesture `useEffect` depends on `handControl` and `running` and **does not schedule any rAF at all when `!handControl` or `!running`** — zero per-frame cost in the common "gestures off, mouse-only galaxy" and "HUD asleep" paths (strictly better than App.tsx's existing loops, which schedule-then-no-op because they can't cheaply read the flag off a prop — this loop can).
- **`readerOpen` must NOT be read as a plain prop inside the loop (H2).** Only the hand pose is safe as an in-loop condition, because it comes from `liveHandRef.current` and is re-read every frame. `readerOpen` is a prop, so an rAF closure created while it was `false` captures `false` forever and the effect never re-runs when a note opens — node-dwell and fist-orbit would keep running *underneath* the open reader, so a fist would both close the reader and orbit the camera (the exact collision D7/R5 exist to prevent), and the `readerOpen` branch of the `controls().enabled` latch restore would silently never fire. Mirror it into a ref written on every render (`readerOpenRef.current = readerOpen`) and read the ref in the loop, or put it in the dep array (it changes at most once per note). Same rule for any other prop the loop consults.
- `onForceClose` must also be forwarded from `VaultGalaxy` down to `GalaxyCanvas` (M5) — today it is consumed only by `GalaxyErrorBoundary`, so the try/catch mitigation below would have nothing to call.
- The per-frame body still no-ops unless the `fg` ref is live, guards `node.x !== undefined` before projecting (no coords before the first sim tick), and `cancelAnimationFrame`s on cleanup (L3). **Alternative considered:** exposing the `fg` ref up to `App.tsx` and running the loop there beside the others — rejected because it leaks the imperative instance out of the component that owns its lifecycle, and the existing App loops are all DOM-oriented (`elementFromPoint`, `scrollTop`) while this one is camera/projection-oriented.

### D6 — The note reader just gets real hand state; `ReaderCore` is unchanged

`NoteReader` (today typed `{ title, markdown, onClose }`, rendered at `App.tsx` alongside — not inside — `HudShell`) gains `hand`/`handRef` props and passes them into `ReaderCore`, plus the gesture-aware footer hint. Crucially, it must **gate `hand={handControl ? hand : null}` exactly as `ReaderOverlay` does (M2)**: `ReaderCore`'s footer hint keys off `hand` truthiness, so passing a non-null `hand` unconditionally would advertise gesture controls even with hand control off — violating the "note reader without hand control is unchanged" scenario. With the gating, `handRef` is passed live for the per-frame scroll/resize loop and `hand` (React state) drives the `useEffect([hand?.fist])` close binding only when hand control is on. `ReaderCore`'s loop is already null-safe and already implements every reader binding, so this is almost purely a wiring change (props on `NoteReader` + the App-level `<NoteReader …>` call site).

**One small `ReaderCore` change is required after all (M-A1).** Its gesture rAF loop is `useEffect(…, [])` — it schedules a frame for as long as *any* reader is mounted, regardless of hand control. With `handRef` now passed live, a note reader opened with hand control off would run a 60 fps loop over `EMPTY_STATE` — exactly the no-op loop the footprint requirement forbids, in the code path that requirement names. So `ReaderCore` takes a `gesturesEnabled` prop in the loop's dep array and schedules nothing when it is false (~3 lines). This also removes the same pre-existing waste for the task run-reader, and is why `two-hand-gestures`' reader requirement gains the "per-frame gesture work only while hand control is enabled" clause. The reader's *binding logic* is still untouched. The single-reader invariant (`openNoteFromGalaxy` clears the task reader) already holds from change #1.

Note `hand`/`handControl`/`handRef` already reach `HudShell` but stop there — the change threads them to `VaultGalaxy` (rendered by `HudShell`, not App) and to the App-level `<NoteReader>`; see D5 and Impact for the exact plumbing hops.

### D7 — Gesture-context arbitration (the authoritative map)

Precedence, highest first:
1. **Reader open** (`openNote != null`): only `ReaderCore`'s bindings run (fist-close, two-palm-resize, palm-scroll). The galaxy gesture loop is suppressed by its own `!readerOpen` guard; the deck loops are already suppressed by `!secondBrainActive`. A fist here closes the reader (its established binding), not the camera.
2. **Galaxy active, no reader**: galaxy node-dwell + fist-orbit + pinch-zoom run; the orb and universal-dwell/scroll loops are already gated off by `!secondBrainActive`.
3. **Neither**: unchanged deck behavior.

Because `openNote` can only be set while `secondBrainActive` is true, the deck loops' existing `!secondBrainActive` guard already covers the reader-open case too — no new guards are needed in `App.tsx`'s existing loops. The one gap to close: **whenever the galaxy goes away, `openNote` must be cleared**, so a note reader is never left mounted over the transparent, click-through HUD with no galaxy behind it.

**Make the note reader's existence derived, not reconciled (M3 → H-A2).** My first cut patched `toggleSecondBrain`/`exitHud`; a review found that misses `toggleDrawing` (which sets `secondBrainActive=false` *directly*) and `onForceCloseSecondBrain`. My second cut — a `useEffect(() => { if (!secondBrainActive) setOpenNote(null) }, [secondBrainActive])` — still misses a **fifth** path and keeps a race:

- `onHudMode`'s "to-deck" branch (the global hotkey and the tray item, as opposed to the HUD button's `exitHud`) clears `drawingActive` but **not** `secondBrainActive`. So on a hotkey exit `HudShell` unmounts (the galaxy is gone) while `secondBrainActive` stays `true`, the effect never fires, and `NoteReader` — rendered at App root, outside the `uiMode` branch — stays mounted **over the deck**. Re-entering the HUD also snaps the galaxy straight back on, which `hud-drawing-canvas` explicitly forbids for its own layer and which the galaxy spec simply never stated.
- `openNoteFromGalaxy` `await`s the note read and *then* `setOpenNote(...)`. If the galaxy closes during that await, the effect has already run and the note mounts orphaned.

So the reader's existence is **derived at the point of use**: `{secondBrainActive && openNote ? <NoteReader …/> : null}`. Separately, `onHudMode`'s to-deck branch clears `secondBrainActive` alongside `drawingActive` so the galaxy is genuinely HUD-only on every exit route.

**Keep the effect too — derivation and reconciliation solve different halves (H1).** My second cut concluded the derived render made the effect unnecessary; that was wrong, and it opens a new hole: derivation suppresses *rendering* but leaves `openNote` **set**. Open a note, leave the HUD by hotkey (the reader correctly disappears), come back and toggle the galaxy on — `secondBrainActive && openNote` is true again and the **stale reader pops open over a freshly-loading galaxy**, breaking the galaxy-view scenario "Toggling the galaxy on shows the vault graph" and reproducing exactly the snap-back-on-re-entry behavior this section exists to prevent. The two mechanisms are complementary: the derived render closes the `openNoteFromGalaxy` await race (an effect cannot — it has already run by the time the fetch resolves), and `useEffect(() => { if (!secondBrainActive) setOpenNote(null) }, [secondBrainActive])` clears the state (derivation cannot). With the `onHudMode` fix landed, `secondBrainActive` now falls on all five close paths, so the effect is complete. **Ship both.**

Both of those are galaxy-layer lifecycle facts, not gesture facts — they are therefore specified as a **MODIFIED delta on `second-brain-galaxy-view`** (which already owns "at most one reader" and "closing the note returns to the galaxy"), not in this change's own capability. That keeps the fix from being silently reverted along with the gesture work, whose stated rollback is "revert the renderer diff".

Also fold `expandedTaskId` into the reader-open signal the galaxy loop reads (L1): `readerOpen = openNote != null || expandedTaskId != null`, cheap insurance against a task reader being open when the galaxy is toggled on.

### D8 — Still gated on the existing hand-control opt-in; no new flag

All of the above runs only when `handControl` is true (the persisted opt-in camera toggle). With it off, `VaultGalaxy` receives `handControl=false`, the gesture loop is never scheduled, and the galaxy is mouse-only exactly as shipped. No `IRIS_*` flag is added — change #1 introduced none for the view, and the hand-control toggle is the natural switch. Rollback = revert the renderer diff; nothing persisted or migrated.

### D9 — Gesture context: extract the shared resolver, adopt it only in new code

The precedence D7 declares is authoritative in prose only — in code it is re-derived independently at seven sites, and the spellings already disagree (the orb loop omits `showHistory`; none of the three deck loops mention `openNote`, working today only via the transitive fact that `openNote ⟹ secondBrainActive`, which H-A2 shows is not robust). Adding an eighth ad-hoc guard would take that from three inconsistent copies to five.

**Decision (scope-limited, user-confirmed):** extract a pure `src/lib/gestureContext.ts` — `resolveGestureContext({ readerOpen, secondBrainActive, drawingActive, historyOpen }) → "reader" | "galaxy" | "drawing" | "history" | "deck"` — with its own unit test, and adopt it **only in code this change touches**: the new galaxy gesture loop and the `handAction` indicator (D10). The three shipped deck rAF loops keep their existing guards untouched, so this change stays additive and carries no regression risk to working gesture behavior. The remaining duplication (and the `showHistory` inconsistency in the orb loop) is recorded as known debt for a dedicated follow-up change that can adopt the resolver everywhere with its own verification pass.

**Alternative considered:** unify the four rAF loops behind a shared `useGestureLoop` hook — rejected. They read genuinely different sources (`elementFromPoint`, scroll containers, orb refs, `fg.camera()`); only the *context derivation* is duplicated, and that is what gets extracted.

### D10 — The action indicator must name the live binding

`handAction` (App.tsx) currently reports `Closed_Fist · idle` whenever `drawingActive || secondBrainActive`, and the reticle's charging state is fed only by the DOM dwell loop (suppressed under the galaxy). After this change a fist under the galaxy *orbits the camera* and a dwell *opens a note*, so the indicator would actively lie — and it is the user's only readout of which binding is live, which matters most precisely because D4 partitions three drives across three poses. `two-hand-gestures` treats the indicator as a spec'd surface, so this is a requirement, not polish: the memo is **restructured to switch on D9's resolved context first**, with a label for every context, rather than growing a fifth nested ternary. Two further lies must be fixed in the same pass (M11): (1) the fist branch tests `expandedTaskId` — the *task* reader — so with a vault note open it falls through to "idle" while a fist actually closes the reader; the `"reader"` context needs its own labels, and this change is what makes that binding live for notes. (2) The two-open-palms early return fires unconditionally *before* any context check, so it would report "Two palms · resize" under the galaxy where two palms resize nothing; it moves inside the reader branch. Reporting galaxy dwell *progress* up to the existing reticle would need a further prop thread and is deliberately out of scope — the in-scene node highlight (D2) is the charging feedback.

### D11 — The HUD control island stays dwell-reachable so the galaxy has a hands-free exit

Suppressing the DOM dwell loop for the whole galaxy layer (D7 step 2) means every galaxy gesture is an *entry* — dwell opens a node, fist orbits, pinch zooms — with **no exit gesture**, in a feature whose premise is hands-free navigation. The CSS already intends otherwise (`hud.css`: the galaxy sits at `z-index: 1` "so the toggle stays reachable to close it"), and `glass-hud-mode` promises `.hud-hit` islands respond "to click **and gesture dwell-click** normally". Fix: the universal dwell loop's layer guard exempts the HUD control island, so `actionable.closest(".hud-controls")` survives the fullscreen-layer suppression while everything beneath the layer stays suppressed. **This requires reordering the loop (M6):** today the layer guard is an early return that runs *before* `elementFromPoint`/`.closest(...)` resolve the actionable element, so there is nothing to test at the point the guard fires. Resolve `actionable` first, then apply the layer guard only when the resolved element is not inside `.hud-controls` — keeping the `[data-no-dwell]` and `expandedTaskId` parts of the guard intact and unconditional. The mechanism itself is sound: `.hud-orb-cluster` is `z-index: 2` against the galaxy's `1`, so `elementFromPoint` genuinely returns the island above the galaxy; the island is shown whenever a hand is present; the galaxy toggle sits outside the `awake` branch so it survives sleep; and an open reader's `.reader-backdrop` covers the screen at `z-index: 40`, so the exemption cannot fire through a reader. This is the smallest change that preserves the layering's stated intent, and it is why the `two-hand-gestures` delta gains the control-island clause.

## Risks / Trade-offs

- **R1 — `3d-force-graph`'s internal TrackballControls call `.update()` every frame and may clobber our `cameraPosition()` writes** → **SPIKE GATE (task 3.1), before building orbit/zoom.** Source check makes the likely answer clear: the render loop guards `state.controls.enabled && state.controls.update(...)`, so `(fg.controls() as any).enabled = false` while a gesture is actively driving cleanly stops the clobber. **Treat `enabled` as a latch that MUST be restored to `true` on every exit from active drive, not just on gesture release (H-2).** "On release" (fist → not-fist) is only one exit; the loop also stops driving when `handControl` toggles off mid-orbit, when `readerOpen` flips true (a note opens), when `running` goes false (HUD sleeps), or on any no-hand frame after an orbit frame — if `enabled` was left `false` in any of these, mouse drag/zoom stays dead for the rest of the galaxy session, violating the "Mouse camera control still works" scenario. So whenever the loop transitions out of actively driving the camera it re-enables controls. **Re-enable target-sync trap (M5):** the controls' `setLookAt` only writes `controls.target` while `enabled` is true, so `target` goes stale while we drive with controls disabled; re-enabling then snaps the camera to orbit the stale target. On re-enable the loop must first `fg.controls().target.copy(center)` (the same explicit center from D3) *before* flipping `enabled` back on — re-reading `fg.controls().target` each time, never caching the reference, because `setLookAt` **replaces** that `Vector3` with a fresh object on every enabled `cameraPosition()` call (L16). The `controls()` cast noted for `enabled` applies here too. **Exception:** the H2 force-close/`try-catch` path does NOT re-enable — `onForceClose` tears the instance down (`_destructor()`), so touching `controls()` there would be a use-after-destroy. Behavior (fist orbits, pinch zooms) is fixed; the spike confirms the lever and records the restore-on-every-exit + re-enable-target steps — the same pattern change #1 used for its bloom/transparency gate.
- **R2 — Dwell false-positives in dense clusters** → nearest-node-within-threshold only, require `Pointing_Up`, and the leave-and-re-enter debounce; tune the pixel threshold during the manual pass.
- **R3 — Camera jitter from hand tremor** → reuse the smoothed point, small per-frame delta constants, and the first-frame-seeds-no-delta guard (D4).
- **R4 — Projecting all nodes each frame is O(n)** → the fixed costs are removed up front regardless of vault size: a reused scratch `Vector3` (no per-node allocation, M-2) and no loop at all while gestures are off or the HUD is asleep (H-1). Beyond that it is fine for typical vaults; if a very large vault is sluggish, project only nodes within the current view frustum / cap per-frame work. Note in the manual pass; not further pre-optimized.
- **R5 — Fist ambiguity between "orbit galaxy" and "close reader"** → resolved by D7 precedence: a fist only orbits when no reader is open, and only closes when one is. Opening a node uses pointing+dwell (not fist), so opening never immediately triggers the reader's fist-close.
- **R6 — A gesture-driven camera or dwell that throws must not trap the fullscreen click-through-disabled overlay** → **the `GalaxyErrorBoundary` does NOT catch this (H2).** React error boundaries catch throws during render/lifecycle only, not inside `requestAnimationFrame` callbacks — so a per-frame throw (e.g. calling `cameraPosition`/`project` on a half-disposed instance during a teardown race) would throw into the void every frame and leave the click-through-disabled overlay trapped, the exact failure this risk names. Mitigation: **wrap the per-frame loop body in `try/catch` and call `onForceClose()` on a caught throw** (the same handler change #1 threads as `onForceCloseSecondBrain`), then `return` to stop the loop. The boundary still covers render-time crashes; the loop must self-guard.

## Migration Plan

Renderer-only, additive, behind the existing hand-control opt-in. No data, IPC, or dependency migration. Deploy = ship the renderer diff. Rollback = revert it; the galaxy returns to mouse-only with no residue (no persisted state, no new flag).

**One carve-out from that rollback.** The galaxy-layer lifecycle fixes (derived note-reader rendering, `onHudMode` clearing `secondBrainActive`) fix a change-#1 bug that has nothing to do with gestures — they are specified as a `second-brain-galaxy-view` delta for exactly that reason, and should survive a gesture rollback. Keep them in separate commits from the gesture work so reverting one does not silently revert the other. Likewise `src/lib/gestureContext.ts` and the `ReaderCore` `gesturesEnabled` prop are independently useful; only the galaxy nav itself is gated behind the 3.1 spike.
