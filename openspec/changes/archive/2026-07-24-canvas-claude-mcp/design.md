## Context

`hud-drawing-canvas` (shipped) established: excalidraw whiteboard as a HUD panel; canonical excalidraw JSON as the one scene format; the renderer pushes scene changes to main (`canvas:scene`), main keeps an **eagerly-updated in-RAM cache** + persists to `~/.iris/canvas.json`, and serves it over `canvas:get-scene`. This change adds an Iris-hosted MCP server so Claude reads that cache and writes back. Grilled decisions (memory `canvas-claude-roadmap`): Claude (PO SDK + DEV/plain CLI) is the reader/writer, not Gemini; Iris main hosts ONE MCP over **Streamable HTTP**; wiring is Iris-scoped per-run (no `~/.claude`); READ+WRITE from the start; gated on `pipelineAvailable`; read returns excalidraw JSON + optional image.

## Goals / Non-Goals

**Goals:** one Iris-hosted HTTP MCP server both Claude paths use; fresh-on-call reads from main's cache; live writes reflected on the open canvas and persisted; secure localhost binding; gated on Claude.

**Non-Goals:** Gemini reading the canvas; hand-gesture drawing; writing MCP config into `~/.claude`; real-time multi-user collaboration/OT merge; a standalone/external MCP process.

## Decisions

### D1 — Transport: one Streamable HTTP server hosted in main, shared by both Claude paths (not stdio, not WebSocket, not per-path in-process)
Because main hosts the MCP **and** owns the canvas cache in the same process, an HTTP endpoint serves directly from the cache — no extra hop. The Agent SDK's `McpServerConfig` supports stdio/SSE/HTTP/in-process; **there is no WebSocket MCP transport**. stdio is rejected: the client would spawn the server as a *separate* process that can't see main's cache (the tldraw-mcp round-trip we avoid). SSE is the deprecated HTTP transport. Use `@modelcontextprotocol/sdk`'s `McpServer` + `StreamableHTTPServerTransport` behind a small Node `http` listener on `127.0.0.1`.

**Transport session mode — stateless.** `StreamableHTTPServerTransport` picks its mode from the `sessionIdGenerator` constructor option: *stateful* (`() => randomUUID()`) mints a session id on `initialize` and 400s/404s traffic that doesn't carry a valid one — a single transport instance then tracks exactly **one** session. But every Claude client does its own `initialize`: the PO SDK session, each DEV/plain subprocess, and each sequential run. Since `runQueue` already guarantees **one Claude at a time**, we use **stateless mode** (`sessionIdGenerator: undefined`, one `McpServer` + one transport) rather than the per-session-transport-map a stateful server would require. The single bearer-token check is orthogonal — it lives in the raw-http wrapper *before* `transport.handleRequest`, unaffected by the transport's own (now disabled) session lifecycle.

_In-process alternative considered and rejected (deliberately):_ PO runs inside the SDK in main's own process, so `createSdkMcpServer` (`McpSdkServerConfigWithInstance`, also supports `alwaysLoad`) would give the PO path the canvas tools with **no HTTP, port, token, or Origin surface at all** — strictly smaller for the primary consumer. But **plain/DEV Claude is a real subprocess** (D7) and cannot use an in-process server, so *some* HTTP transport must exist regardless. We keep **one** HTTP server shared by both paths (single surface, single set of tool handlers) rather than maintain two server surfaces (in-process for PO + HTTP for subprocess). Accepted trade-off: the PO path carries the HTTP/token/Origin surface even though it is co-located with the server — mitigated by loopback + ephemeral port + per-session token + Origin check (D2). Chosen for consistency and one place to reason about auth.

### D2 — Security: right-sized for a local-only server (loopback + ephemeral port + one token)
This server **only ever talks to local Claude** on the same machine — it is not a public/internet endpoint, so the elaborate hardening appropriate for a public MCP (DNS-rebinding protection, `Origin`/`Host` allowlists, per-method guard ceremony) is deliberately **not** applied; it would be borrowing an internet threat model that does not fit. The guard is minimal and cheap:
- Bind to `127.0.0.1` only + choose an ephemeral port at startup.
- Require **one** `Authorization: Bearer <token>` where the token is a random per-session secret, handed only to Iris's own Claude runs (SDK option / `--mcp-config`), never persisted to `~/.claude`.

The single token is kept (not dropped) because it is essentially free and it is the one thing that closes the only realistic local vector: without it, any web page the user opens in a browser could `fetch` `http://127.0.0.1:<port>` and drive the canvas. With it, such a page cannot (it can't know the per-session token). That is the whole threat model; nothing more is warranted.

### D3 — Read tool: serve main's eager cache, optional rendered image via a request/response IPC
The read tool returns main's in-RAM cache (the change-1 seam) → fresh-on-call, works while the panel is unmounted. Payload is the canonical excalidraw JSON; an `includeImage` option renders PNG/SVG. Rendering an image headlessly in main is impossible: excalidraw cannot even be imported in the main process (its only build entry pulls `roughjs/bin/rough` and touches `window`/`document` at load), so **main never imports excalidraw** — all excalidraw calls live in the renderer. When the panel is mounted, main asks the renderer to export via excalidraw's `exportToBlob`/`exportToSvg` over a **request/response IPC** (`canvas:request-image` main→renderer with a correlation id; the renderer replies on `canvas:image-result`; main resolves a pending-promise registry keyed by that id, with a timeout so a mid-teardown panel can't hang the tool). When the panel is not mounted, return JSON only (image omitted). Document this limitation.

### D4 — Write authority: last-writer-wins over main's cache; renderer replaces whole-scene, with echo suppression
Brainstorming is turn-based (Claude acts in a turn; the user watches), not concurrent editing, so a full OT/CRDT merge is unnecessary. **Reality of the shipped seam (change 1):** the `canvas:scene` handler is a *whole-scene replace* (`canvasStore.setScene(scene)`) — there is **no id-level merge in main**. So the honest model is **last-writer-wins**, not a fully authoritative main cache: main holds the working copy and a Claude write mutates it **by element `id`** (add / replace / remove, using the pure main-side element builder from D5 — never excalidraw), persists, and, if the panel is mounted, sends `canvas:apply` so the renderer merges into the live scene via excalidraw `updateScene`. But whenever the panel is mounted, the renderer's own user edits flow up via `canvas:scene` as a **whole-scene replace** — at that instant the renderer is effectively authoritative and main accepts its scene wholesale. So the true invariant is: *last-writer-wins; concurrent same-element edits by user and Claude are not merged.*

**`canvas:apply` carries the FULL post-write element set, not a delta.** excalidraw's `updateScene({ elements })` **replaces** the entire elements array (verified against the installed type) — it is not a patch. So a Claude-originated apply sends the **complete** element set from main's cache (main already holds the whole scene and mutates it by id), and the renderer calls `updateScene` with that full set — which also naturally expresses deletes. It must **not** send only the changed elements (that would delete every user element) and must **not** re-run `convertToExcalidrawElements` renderer-side (main already built complete elements per D5; that helper is only for skeletons). The apply uses `captureUpdate: CaptureUpdateAction.NEVER` (excalidraw's documented option for *remote* updates) so Claude writes don't pollute the user's undo stack.

Because `canvas:apply → updateScene → onChange → canvas:scene → setScene` forms a **loop**, a Claude-originated apply must not be echoed back as a fresh whole-scene write that could clobber the cache with a slightly-stale renderer copy captured mid-apply. The renderer therefore **suppresses the `canvas:scene` echo for a Claude-originated `canvas:apply`**. A bare "skip the next `onChange`" boolean is unsafe: `updateScene` may fire `onChange` **zero** times (excalidraw no-ops when it sees no visible delta, leaving the flag armed to swallow the next genuine user edit) or **more than once**. Prefer a robust guard — diff the incoming `onChange` scene against the just-applied element set, or a scene-version/nonce comparison — not a one-shot flag. Echo suppression narrows the race but does **not** close it: a user edit whose debounced `onChange` snapshot was captured *before* a Claude apply landed will still push a pre-apply whole scene and drop Claude's element. This residual is accepted as rare (turn-based use) and last-writer-wins.
_Alternative A:_ renderer stays sole authority and main forwards writes only when mounted — rejected: writes would be impossible/lost while the panel is closed, and the read cache could disagree with applied writes.
_Alternative B (future hardening, not now):_ move the `canvas:scene` handler to an **id-level merge** in main so the renderer stops clobbering by-id writes — the only change that would fully close the residual. Out of scope; noted so a future need has a known lever.

### D5 — Tool set (small but sufficient), elements built pure in main
- `get_canvas({ includeImage?: boolean })` — read.
- `add_elements({ elements })` — create rectangles/ellipses/diamonds/text/arrows/lines; arrows/connectors may reference existing element ids for `startBinding`/`endBinding`.
- `update_elements({ elements })` — patch by id.
- `delete_elements({ ids })` — remove by id.
Claude passes a **concise skeleton** (type + geometry + text + bindings). Because excalidraw **cannot be imported in main** (D3), main does **not** use `convertToExcalidrawElements`; instead a small **pure element builder in main** expands each skeleton into a full excalidraw element, filling every required field (`id, type, x, y, width, height, angle, strokeColor, backgroundColor, fillStyle, strokeWidth, roughness, opacity, seed, version, versionNonce, updated, groupIds, boundElements, …`) — excalidraw silently drops elements missing required fields, so this must be complete. (`convertToExcalidrawElements` is still fine to use renderer-side in the `canvas:apply` handler, which runs in browser context.) The builder is the feature's core correctness risk (a missing field is an invisible drop, and the field set rots when excalidraw bumps), so it is verified against excalidraw's real `convertToExcalidrawElements` as a golden reference (tasks 7.x), not against a hand-enumerated list, and the excalidraw version is pinned so a bump is a test-gated event.

**Invalid / dangling write input.** Under `bypassPermissions` Claude will occasionally emit `update_elements`/`delete_elements` for an unknown id, an `add_elements` id collision, or an arrow whose `startBinding`/`endBinding` references a nonexistent or just-deleted element. Rather than silently drop (invisible to Claude, so it can't self-correct), each write tool returns a **per-element result** — `applied` / `skipped: unknown-id` / `rebound: dropped-binding` — and bindings are validated against the **union of the existing cache and the current add batch**. A structured result is what lets a turn-based agent fix its own mistake.

### D6 — Lifecycle: gated on pipeline availability **AND canvas-engaged**, plus a server-ready signal
Two conditions gate the MCP, not one: `pipelineAvailable` (Claude present) **and `canvasEngaged`** — a **sticky** per-session flag set the first time the drawing panel is opened. Rationale (token cost): wiring the MCP means loading the tool schemas into Claude's context on every turn (`alwaysLoad`, below); a pure-voice session that never touches the canvas should pay **zero** for a capability it isn't using. So:
- **Neither** condition met, or canvas never engaged this session → **no server, no wiring** → zero token overhead. The whiteboard itself is unaffected (`hud-drawing-canvas` is not Claude-gated); this only withholds the *AI* read/draw wiring.
- Canvas engaged (panel opened ≥1 time) **and** Claude present → start the server and wire it. **Sticky matters:** "opened then closed" ≠ "never opened" — once engaged, the wiring stays for the rest of the session even while the panel is toggled shut, which preserves the specced "Claude reads/writes while the panel is closed" scenarios. Only a session that *never* opened the canvas skips it. The flag resets on app restart.

Reuse the existing `probePipelineAvailability()` signal for the Claude half; the canvas-engaged half is a new main-side flag set from the panel-open signal the renderer already reports. Stop the server on quit (via the `app-shutdown` teardown). The ephemeral port and thus `{ url, token }` are only known inside the `listen` callback, so expose **server-ready as a resolved promise/state** that the run paths await before wiring — a PO turn or DEV/plain spawn that fires before the listener is up must either wait for ready or wire cleanly with no canvas MCP (never an `undefined` URL). If Claude becomes available (or the canvas is first engaged) mid-session, bring the server up and, for a live PO session, call `query.setMcpServers()` so it gains the tools without a respawn.

_Why gating, not a skill:_ a skill telling Claude "only call the canvas tools when relevant" is soft (Claude may ignore it) and itself costs context tokens, and it does **not** save the per-turn schema cost. Hard-gating the *availability* on canvas-engaged is reliable and saves both the schema tokens (tools absent when idle) and stray `get_canvas` scene pulls. "How to use" is covered by the light persona line + tool descriptions (D7); no skill is warranted.

**Tool visibility (`alwaysLoad`).** The Agent SDK defers MCP tools behind tool-search by default (`McpHttpServerConfig.alwaysLoad` doc: *"tools are deferred when tool search is enabled"*). Once the MCP *is* wired (canvas engaged), Claude must see `get_canvas`/`add_elements` in the first turn without a search, so set **`alwaysLoad: true`** on the HTTP config on **both** the PO `options.mcpServers` entry and the DEV/plain `--mcp-config` JSON. Documented side effect: `alwaysLoad` blocks turn-1 setup until the server connects (≈5s cap) — another reason the server-ready gate above matters. (The engaged-gate and `alwaysLoad` are complementary: the gate decides *whether* the tools load at all; `alwaysLoad` decides they load eagerly *once* they're in play.)

### D7 — Persona / discoverability (light), and which Claude path
So Claude actually uses the tools when asked about "the diagram," add a brief line to the persona/chat surface that a canvas MCP is available for reading/annotating the user's drawing. The natural consumer is **PO (SDK) or plain Claude** — DEV is refused by `startClaudeRun` unless there's an open OpenSpec change with unchecked tasks, so canvas Q&A ("what should I add?") is not a DEV task. Wiring DEV is harmless (and kept for symmetry), but the persona line and Gemini routing should steer canvas Q&A to PO/plain, not imply DEV is the canvas consumer. Keep the persona text minimal; the tool descriptions carry the detail.

### D8 — Module boundary, failure modes, observability
**Own module.** The MCP subsystem lives in its own `electron/canvas-mcp.mjs` (server lifecycle, HTTP listener + auth, tool handlers, the pure element builder), mirroring the existing `canvas-store.mjs`/`po-session.mjs` seams — `main.mjs` (already ~3300 lines) stays the wiring point only. The module receives its dependencies injected (a cache getter, an apply-broadcast callback, a persist callback, and an image-request function), which keeps the tool logic and element builder **pure/unit-testable** without `app`/`ipcMain`/`BrowserWindow`.

**Cache mutation is read-modify-write; scene may be `null`.** `canvas-store.mjs` exposes only `getScene`/`setScene`/`flush` — there is **no** by-id API. So "mutate by id" = `getScene()` → transform the whole scene → `setScene(next)` → `flush()`. `getScene()` returns **`null`** on a fresh machine (no `~/.iris/canvas.json`) — `get_canvas` and every write's read step must treat `null` as an empty scene, never crash. Note the store's oversize branch: `setScene` skips `pendingJson` when the serialized scene exceeds `maxBytes`, so a `flush()` after an oversized write persists nothing (RAM-only) — consistent with change 1, not a durability bug.

**`po-session.mjs` stays canvas-ignorant, but Task 5.1 is a signature change, not a pass-through.** `getOrCreatePoSession` destructures a **fixed** param set and builds `options` internally — there is no generic options bag to forward through. So: (1) add a new **named param** (e.g. `mcpServers`) that gets set into `options.mcpServers` at create — po-session still forwards an *opaque* record and learns nothing about canvas (isolation preserved), but it *is* an API change; (2) add a **live-session setter** mirroring `setPoSessionModel` (call it `setPoSessionMcpServers`, wrapping `query.setMcpServers()`) plus `currentMcp` tracking on the session state; (3) apply it **lazily per turn** in `startPoRun` exactly like the model check (`state.currentMcp ? Promise.resolve() : setPoSessionMcpServers(state, servers)`), after awaiting server-ready — there is no "enumerate all live sessions" export, so the lazy-per-turn path (not an event-driven "server came up → update every session") is deliberately chosen to avoid new plumbing.

**Failure modes / graceful degradation.** (a) The raw `http.Server` MUST register an `'error'` handler — an unhandled `'error'` event throws and would crash Electron main; ephemeral port (`0`) makes `EADDRINUSE` unlikely but bind failures still happen, and must fail the server-ready promise cleanly (no server, whiteboard unaffected). (b) If the listener dies mid-session, a live PO session still holds the URL/token; its canvas tool calls surface as **MCP tool errors** (Claude sees them and can react) and never crash main, and server-ready flips back to false so new runs wire cleanly with no canvas MCP. (c) `get_canvas({ includeImage })` on IPC timeout (panel tearing down) **degrades to JSON-only**, never a tool error. (d) A Claude write forces a store `flush()` (see below).

**Durability of Claude writes.** Clean quit already flushes the store (`shutdownTeardown`), but a write while the panel is closed otherwise sits in the store's ~2s debounce with a best-effort `flush()`. Claude writes are low-frequency and carry a higher durability expectation than individual user strokes, so each MCP write **forces a flush** — cheap, and makes the spec's "persisted" guarantee real immediately.

**Observability.** For a security-sensitive localhost server, log at minimum: server-ready `{ port }` once; **every auth/Origin rejection** (the only signal another local process is probing the endpoint); and each tool call with element counts. Nothing more.

## Risks / Trade-offs

- **excalidraw cannot run in main** (import fails: `roughjs`, `window`/`document`) → main never imports excalidraw; a pure main-side element builder constructs elements, image export is delegated to the renderer over IPC (D3, D5).
- **MCP tools deferred behind tool-search by default** → `alwaysLoad: true` on both wiring paths so canvas tools are visible turn-1 (D6).
- **Headless image export in main** (no DOM) → only export images when the panel is mounted (renderer does it, via request/response IPC with a timeout); JSON-only otherwise (D3).
- **Write echo loop / clobber** (`canvas:apply → onChange → canvas:scene`) → suppress the echo for Claude-originated applies; turn-based usage + last-write-wins otherwise (D4).
- **Server-ready races run-start** (ephemeral port known only in `listen`) → server-ready promise the run paths await; re-wire a live PO session via `setMcpServers` when ready (D6).
- **Localhost server exposure** → right-sized: loopback bind + ephemeral port + one per-session token (the token blocks the only realistic local vector — a browser page fetching localhost); no internet-grade DNS-rebinding/Origin hardening (D2).
- **DEV token visible via `ps`** (inline `--mcp-config` JSON in argv) → a local-multi-user concern we don't model on a single-user desktop; inline is acceptable, a `0600` temp file is a cheap optional nicety, not required (D2 / tasks).
- **MCP config staleness** → per-run injection with the live URL/token; nothing written to `~/.claude`, so a stopped server never leaves a broken entry.
- **New dependency** `@modelcontextprotocol/sdk` → already present transitively (1.29.x); add as a direct exact-pinned dep, don't lean on the transitive copy.

## Migration Plan

Additive; no data migration. Rollback = stop hosting the server, drop the dependency and the write-apply path; `hud-drawing-canvas` and the rest of the pipeline are unchanged. The seam it consumes (`canvas:get-scene`) already exists.
