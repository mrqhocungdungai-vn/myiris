## Context

Iris writes a second-brain vault at `~/iris-second-brain` (`personal-knowledge-notes`) as plain markdown with YAML frontmatter and `[[wikilinks]]`, but has no viewer. The user wants a cinematic 3D "galaxy" of the vault inside Glass HUD mode, inspired by the Obsidian plugin **galaxy-view** (`longwind1984/galaxy-view`, MIT).

Constraints established during grilling + a Senior Developer pre-implementation review (2026-07-24):

- **galaxy-view is not embeddable.** It is an Obsidian plugin whose data layer reads the graph through Obsidian's API (`app.metadataCache`, `app.vault`); only its Three.js `render/` layer is theoretically reusable, and it was never published as a standalone library. So we **do not copy its code** — visual inspiration only.
- **The stack already has the 3D toolbox.** `three@^0.181.2`, `@react-three/fiber`, and `@react-three/postprocessing` are present (`ReactorCore`, `HoloBackdrop`). The HUD already owns one live WebGL canvas (`ReactorCore`); adding the galaxy adds a second. We deliberately avoid a *third* by making the deep-space backdrop plain CSS/DOM (D4).
- **The HUD already has the patterns we need.** A toggleable, lazily-loaded layer (`drawingActive`/`DrawingCanvas` + `PenTool` button), a main-owned data store with RAM cache + debounced disk (`canvas-store.mjs`), a markdown reader with gesture hooks (`ReaderOverlay`), and the `.hud-hit` click-through model (with a hard-coded backdrop allowlist in `App.tsx`).
- Renderer cannot read the filesystem directly; a main-process owner must serve the graph over IPC.
- The vault is **not empty on first run**: `ensureNotesVaultReady` (main.mjs) pre-seeds `wiki-config.md` + `wiki-schema.md`, and the LLM-Wiki config references `templates/`/`raw/`/`archive/`/`ingested/` subfolders. The scan must exclude this plumbing.

This is **change #1 of two**. Hand-gesture control (raycast dwell-to-open, fist/pinch camera nav, NoteReader gesture bindings) is deferred to `second-brain-gesture-nav`; this change is mouse/click-first.

## Goals / Non-Goals

**Goals:**
- Render `~/iris-second-brain` as a live 3D link-graph galaxy inside the Glass HUD.
- Own and parse the vault graph in the main process; keep it fresh via `fs.watch` with a renderer-side position-preserving update.
- Open a node's markdown in a note-reader overlay.
- Make viewing work with or without the Claude pipeline; gate only on the vault existing.
- Immersive opaque deep-space backdrop; mutually exclusive with the drawing panel.

**Non-Goals:**
- Hand-gesture control of the galaxy or reader (→ `second-brain-gesture-nav`).
- Editing notes from the galaxy (read-only view; writing stays with `personal-knowledge-notes`).
- Configurable vault path or multi-vault (vault fixed at `~/iris-second-brain`).
- In-scene 3D note panels (CSS3D billboards).

## Decisions

### D1 — Render with `3d-force-graph` (vanilla), not a galaxy-view fork or an r3f-native scene

Use **`3d-force-graph`** (vanilla, Three.js-based, MIT), fed a `{ nodes, links }` object. It ships the force simulation, camera/orbit controls, node/link rendering, **and its own post-processing composer** (`.postProcessingComposer()`), which is what makes D4's node-bloom achievable while keeping the lib (see H1 below).

- **Alternatives considered.** (a) *Fork galaxy-view's `render/` layer* — rejected: high cost untangling Obsidian coupling, we'd own a fork. (b) *Port the plugin with an Obsidian API shim* — rejected: most work, most fragile. (c) *Hand-build an r3f scene with `d3-force-3d` + `@react-three/postprocessing`* — viable and maximally consistent with `HoloBackdrop`, single WebGL context, but requires writing the render/interaction layer ourselves and adds `d3-force-3d`. Kept only as a **fallback** if `three` cannot be deduped (D2). We chose the vanilla lib because it satisfies bloom-on-nodes via its own composer and minimizes hand-written rendering.

### D2 — One `three`, deduped at the bundler (no API to inject it); add a frontmatter parser

`3d-force-graph` bundles/depends on its own `three`; the app already resolves `three@^0.181.2` via r3f. There is **no API** to hand the lib an external `three` — dedupe is purely a resolver concern. **Reality check (verified):** the app does **not** have a single `three` today — `@react-three/drei → stats-gl@2.4.2` pins `three@^0.170.0` and ships a nested `node_modules/stats-gl/node_modules/three@0.170.0`, so `npm ls three` already prints two copies before this change. `3d-force-graph@1.80.0` declares `three: ">=0.179 <1"`, which **accepts** `0.181.2`, so an `overrides.three` pin is viable.

- Pin `3d-force-graph` **exact**; add `resolve.dedupe: ['three']` to `vite.config` **and** an npm `overrides.three` pin. **Sequence matters:** land `overrides.three` first and confirm it collapses the *pre-existing* `stats-gl` copy (0.170 → 0.181, an untested bump — verify `stats-gl`/`three-stdlib`/drei still function at 0.181.2), and only **then** add the `npm ls three` single-copy gate to `npm run build`/CI — otherwise the gate red-flags a condition that predates this change. If the override breaks drei/stats-gl, scope the gate to "`3d-force-graph` resolves to the app's `three`" rather than a global single copy, or fall back to D1(c).
- **Frontmatter parser (H3):** there is no YAML/frontmatter lib in the repo. Add **`gray-matter`** (pinned exact) and list it in README's exact-identifier table beside `3d-force-graph`. Hand-rolled `tags` parsing is rejected (block/flow/scalar/CSV shapes are a footgun).

### D3 — Main owns the graph data; the RENDERER owns positions; full graph on the wire (no delta)

`electron/vault-graph.mjs` is a `createVaultGraph({ dir })` **factory** (like `createCanvasStore`) returning `{ getGraph, start, stop, onUpdate }` — closure state, no module-level singleton, so it is unit-testable (L-3). It scans `~/iris-second-brain`, builds a **position-free** `{ nodes, links }`, caches it in RAM, and serves it over IPC (`secondbrain:get-graph`). The **pure parsing** (file contents/paths → position-free graph) lives in a separate `electron/vault-graph-parse.mjs` with **no fs/IPC**, so the defect-prone logic is directly unit-testable (M1) — the watch/cache/IPC shell just wraps it. `fs.watch(vault, { recursive: true })` → coarse debounce → **rebuild-from-scan** → push the **full current position-free graph** on `secondbrain:graph-updated`.

- **Full graph each push, not a delta (H-2).** `get-graph` (invoke, snapshot) and `graph-updated` (event) carry the **same** full position-free shape. There is no sequencing guarantee between an async `get-graph` fetch and the event stream, so a wire-delta could reference a baseline the renderer doesn't hold yet. Main rescans fully every fire anyway, so a full payload costs ~the same as a delta. The renderer diffs in **one** place (below); whichever message arrives last is self-consistent and idempotent. A wire-delta is a later optimization behind measured need, not designed in now.
- **Positions live in the renderer, not main (H2).** `3d-force-graph` writes `x/y/z/vx/vy/vz` onto node objects in the renderer's simulation; main never has them. The **renderer** keeps a `Map<id, nodeObject>`, and on every received graph (initial or update) reconciles: mutate matched ids **in place** (preserve `x/y/z`, update label/tag/ghost fields), add new ids, drop missing ones, then pass the **same object references** back to `.graphData()`. This position Map is **hoisted above the lazy galaxy layer** (kept in `App.tsx`/a ref that outlives the `React.lazy` boundary) so toggling the galaxy off and on **rehydrates** positions instead of re-scrambling on every reopen (M-3).
- **"Preserved" ≠ "stable"; motion must be actively managed (M-B).** `.graphData()` re-initializes the force engine and resets the simulation alpha on **every** call, so reused node objects start from their current spots but the sim still **re-runs and drifts** on each `fs.watch` fire. To keep the graph from visibly jiggling when only one note changed: pin unchanged nodes (`fx/fy/fz`) across a reconcile and/or set `warmupTicks(0)` / a low `d3AlphaTarget` / short `cooldownTicks` when the topology is unchanged, and only truly reheat when nodes/links actually changed. This is a real implementation task, not a free property of `graphData()`.
- **Parsing rules.** Only `.md` files are notes — the scanner filters to the `.md` extension **and** `isUserNote` (else a stray `screenshot.png`/`.pdf` at the vault root would pass the exclusion predicate, be fed to `gray-matter`, and become a garbage node — M-D). Node id derived from the note's vault-relative path (basename for the flat vault the capture path produces; disambiguate by relative path if subfolders collide — M3). Wikilink resolution is **case-insensitive** (Obsidian semantics; matters on case-insensitive APFS) via a lowercased target map. Forms `[[Note]]`, `[[Note|alias]]`, `[[Note#heading]]` resolve to the base note. A link to a missing note yields a **ghost** node (`ghost: true`, rendered faded). `[[...]]` inside fenced/inline code and `![[embed]]` transclusions are **skipped** (no spurious links/ghosts). Frontmatter parsed with `gray-matter` **per note inside try/catch** — `gray-matter` throws on malformed YAML, so a single hand-edited bad frontmatter must degrade that note to a tagless (or flagged) node, **never abort the whole scan** and blank the galaxy (M-C). `tags` (any shape) drive node color grouping.
- **What is a user note is owned by the notes capability, not re-listed here (H-1).** The scan must exclude LLM-Wiki plumbing, and that set is a fact of `personal-knowledge-notes`/LLM-Wiki that keeps evolving — it is **not** ours to fork. `personal-knowledge-notes` SHALL expose a single authoritative predicate (a helper beside `NOTES_VAULT_DIR`/`ensureNotesVaultReady` in main) — "is this vault path a user note" — covering the system files (`index.md`, `log.md`, `wiki-config.md`, `wiki-schema.md`) and plumbing folders (`templates/`, `raw/`, `archive/`, `ingested/`). `vault-graph.mjs` **consumes** that predicate. (Reading excludes from `wiki-config.md` alone is insufficient: `renderNotesVaultConfig` writes `blacklist: []` and `index_excludes` omits `index.md`/`log.md`.) Note `index.md` is the catalogue linking to every page — leaving it in would make a mega-hub that distorts the whole layout. "No notes" means "no *user* notes."
- **fs.watch robustness (M2).** Recursive watch (supported on macOS, and Iris is macOS-only); coarse debounce; rebuild-from-scan absorbs editor atomic-save noise (temp file + rename) and any missed event; wrapped in try/catch (watching a not-yet-existing dir throws — see D7).
- **Scan/parse is async, off the event loop (H1).** The main process is a single Node loop shared with the **Gemini Live** websocket and the 16/24 kHz audio IPC. A synchronous `readFileSync` + `gray-matter` loop over a large vault blocks that loop for tens-to-hundreds of ms **on every debounced rebuild** — and rebuilds burst exactly while Claude is capturing notes mid-conversation → audible audio dropouts. So scan+parse use `fs.promises.readFile` with bounded concurrency that yields (mirroring `canvas-store`'s deliberate async write), or offload to a `utilityProcess`/`worker_thread` that posts back the finished `{nodes,links}`. Debounce cuts frequency, not per-scan block duration — this is a `main-thread-budget` concern and a real task.
- **Watcher lifecycle scoped to galaxy-active (M-2), and tied to renderer teardown (M3).** The primary writer to this vault is **Claude during note capture** (every plain-Claude run calls `ensureNotesVaultReady`), so an always-on recursive watcher would rebuild constantly during normal use for a view that is **off by default**. So *freshness* (the watcher) is scoped to the galaxy layer: `start()` on toggle-on (after a fresh scan for `get-graph`), `stop()` on toggle-off and on window-close/app-quit. `start()` is **idempotent** (a no-op if already watching) so HUD open/close churn can't stack FSEvents streams, and the watcher is also stopped on `webContents` `render-process-gone` and renderer reload/navigation (a reload does **not** fire window `"closed"`, so a stream would otherwise orphan while the fresh renderer starts a second one). **`stop()` must also clear the pending debounce timer and set a stopped-guard** so an in-flight rebuild (or a resolving async scan) does not emit `secondbrain:graph-updated` after toggle-off — otherwise a stale event races a fresh `get-graph` on the next open (M-E). *Availability* (does the vault exist) is handled separately (D7) and needs no watcher.
- **Subscription cleanup contract (M4).** `secondbrain:graph-updated` (and the availability subscription) MUST follow the existing preload pattern (`onCanvasApply` at preload.cjs) of **returning an unsubscribe closure**, and the `React.lazy` galaxy layer's `useEffect` MUST call it on unmount — otherwise each toggle-on stacks another listener.
- **Alternatives.** Parsing in the renderer via a thin fs bridge (rejected: off-pattern) or Claude emitting the graph (rejected: token cost + Claude-dependency for a pure-view feature).

### D4 — Immersive backdrop as opaque CSS deep-space; node bloom via the lib's own composer

The bloom-on-nodes requirement cannot be met by an r3f `EffectComposer` post-processing the graph, because `3d-force-graph` renders on its **own** canvas/GL context that r3f cannot touch (H1). The observable requirements are behavior-level and fixed: **opaque immersive deep-space** that occludes the wallpaper, and **glowing nodes**. The *mechanism* is a **spike gate**, not a settled fact, because the two obvious mechanisms are in tension (H-A):

- `UnrealBloomPass` via `3d-force-graph`'s `.postProcessingComposer()` typically writes an **opaque** result (the composite blends over black and forces alpha→1), which would occlude any CSS layer *behind* a transparent graph canvas — defeating a CSS backdrop. And the lib is not installed yet, so transparent-canvas + composer coexistence is **unverified** on the pinned version.
- **Spike resolved (2026-07-24, static — traced the pinned versions' actual source rather than a live render, since the code path is deterministic and fully traceable): composer bloom forces full-screen opacity; the CSS-backdrop mechanism (3.2a) is infeasible.** Traced `node_modules/three-render-objects` + `node_modules/three/examples/jsm/postprocessing/{RenderPass,UnrealBloomPass}.js` at the exact pinned versions (`3d-force-graph@1.80.0`, `three@0.181.2`):
  - `RenderPass` (no explicit clearColor/clearAlpha) clears using the renderer's *current* clear color/alpha, so `.backgroundColor('rgba(0,0,0,0)')` does make the base scene render transparent where nothing is drawn — the base pass alone would support 3.2a.
  - But `UnrealBloomPass`'s composite fragment shader **hardcodes `gl_FragColor = bloomStrength * (... * vec4(tint, 1.0) * texture2D(...) + ...)`** — alpha is a literal `1.0`, not derived from scene coverage. Its final `blendMaterial` (a `CopyShader` clone, `blending: AdditiveBlending`, no `blendFuncSeparate`) then draws that alpha-1 texture via a **full-screen quad** additively onto the screen framebuffer. Additive blending's default (shared RGB+alpha) factors make the resulting alpha `srcAlpha·1 + dstAlpha·1`, clamped to 1 — i.e. **every pixel the full-screen quad touches becomes opaque**, not just bloom halos. Since the quad covers the entire viewport, the composer's last pass opacifies the whole canvas unconditionally whenever bloom is enabled, independent of where nodes/links are.
  - Conclusion: transparent-canvas + `.postProcessingComposer()` do **not** coexist on this pinned version — 3.2a is infeasible as designed. **Mechanism is 3.2b**: paint the deep-space backdrop **inside the graph scene** via `.backgroundColor('rgba(5, 6, 12, 1)')` (opaque near-black) + a points/skybox starfield, so the composer's forced-opaque output *is* the intended backdrop rather than an accidental one. No separate CSS deep-space layer is built for the galaxy (unlike drawing panel/deck, which stay transparent) — one graph canvas, one glow mechanism, behavior identical to the user (opaque immersive backdrop + glowing nodes).
- Where feasible reuse `deepspace-skin`'s `hud-vignette`/nebula vocabulary + `tokens.css` so the backdrop reads as the same visual system (L-2).
- The backdrop mounts only while the galaxy is active; disabling it restores the transparent HUD.
- **Alternatives.** r3f `@react-three/postprocessing` bloom over the graph (rejected — H1, impossible across canvases); flat `#000` (allowed, less cinematic); a WebGL starfield as a second r3f canvas (rejected — extra GL context for no gain).

### D5 — HUD integration: new toggle, fullscreen layer, single active-layer invariant

Add `secondBrainActive` state and a new control button beside `PenTool` (a network/brain icon). The galaxy is a **fullscreen `.hud-hit` layer** (interactive; main disables click-through while it's up), lazily loaded like `DrawingCanvas`. A single "active HUD layer" invariant: enabling the galaxy sets `drawingActive = false` and vice-versa — avoids two heavy WebGL layers and gesture ambiguity (which matters for change #2).

- **Reader single-instance (L3, enforced in THIS change).** The galaxy's `NoteReader` and the task `ReaderOverlay` must not stack; at most one reader (task or note) is open. This mutual exclusion is wired **now** (not deferred) — only the *gesture* bindings for the note reader are deferred to change #2, which will additionally fold the note-reader-open state into the gesture guards that today key off `expandedTaskId`.
- **Cross-capability invariants are documented, not hidden (M-4).** The single-active-layer rule gives the drawing panel a **new close trigger** (it closes when the galaxy opens) that `hud-drawing-canvas`'s spec doesn't know about, so this change carries a small **MODIFIED delta to `hud-drawing-canvas`** capturing mutual exclusion among HUD layers. The reader single-instance invariant is stated as a requirement in this capability's own spec.
- **Alternatives.** Coexisting layers (rejected: double GPU + gesture ownership ambiguity); a separate top-level `uiMode` (rejected: abandons the transparent-HUD philosophy for no gain).

### D6 — Opening a node: `NoteReader` on a `ReaderCore` extracted from `ReaderOverlay`

`ReaderOverlay` already renders markdown (`react-markdown` + `remark-gfm`) and carries the gesture core (fist-close, two-palm-resize, palm-scroll) — but its header is task-shaped (status/agent/session badges) and it imports `normalizeMarkdown`/`shortRunId` from `lib/tasks`. Critically, its wrapper class **`.reader-backdrop` is hard-listed in `App.tsx`'s click-through allowlist (line ~422)** and styled in `hud.css`/`overlays.css`.

- Extract an inner **`ReaderCore`** that keeps the `.reader-backdrop`/`.reader-card` DOM + gesture/scroll/zoom logic + Esc/X close, and accepts `{ title, body, footerHint, headerSlot }` where `body` is a **rendered node** (the caller supplies the markdown-rendered content). `ReaderOverlay` passes its task badges via `headerSlot` and renders `normalizeMarkdown(task.output)` into `body` (behavior unchanged — the task-reader smoke check must still pass). `NoteReader` renders `react-markdown`+`remark-gfm` over the note markdown into `body` itself and passes no `headerSlot`. The palm-scroll rAF loop is already null-safe (`h?.hands … ?? []`), so `NoteReader` passing `hand={null}` in change #1 won't crash.
- **Keep the shared backdrop class in the allowlist** (or add `NoteReader`'s class to line ~422) or it will be click-through-dead and unstyled in HUD.
- In this change `NoteReader` opens on **click** and closes on **X/Esc**; gesture bindings are deferred to change #2 but the shared core is structured for them now.
- **Alternatives.** Fake `TaskCard` reuse (rejected: nonsensical chrome); a fully separate note card duplicating gesture code (rejected: duplication right before change #2 needs the core); CSS3D billboard (rejected: complex, couples to camera, can't reuse reader gestures).

### D7 — Gating on vault existence, independent of Claude, with an explicit sync signal

The toggle is offered iff `~/iris-second-brain` exists — **not** gated on `pipelineAvailable`. Empty vault (no *user* notes) → empty-state. Iris does not create the vault to show the toggle (creation stays in the note-capture path).

- **Sync (M4/M-5).** Re-check `fs.existsSync(NOTES_VAULT_DIR)` on each HUD open, and emit availability **only on the false→true (or true→false) transition** — not on every capture. `ensureNotesVaultReady` runs at the top of *every* plain-Claude run and its `mkdirSync` is idempotent, so a naive "emit after mkdir" would fire constantly; instead track the last-emitted value and emit on change, exactly like `pipeline_availability` does (main.mjs). Availability rides the **existing `sidecar:event` stream** (consumed via `onSidecarEvent`, the same channel `pipeline_availability` uses) — no new dedicated preload channel for this small flag (L2). The large `secondbrain:graph-updated` payload keeps its **own** channel, out of the sidecar log stream. On disappearance, force-close the galaxy layer and hide the toggle. Availability needs **no watcher** — it is `existsSync` + this transition event; the `fs.watch` freshness watcher is a separate, galaxy-scoped concern (D3) and is only started once the vault exists (it throws otherwise).

### D8 — Note reads are by node id, resolved in main (never by renderer-supplied path)

Add `secondbrain:read-note` taking a **node id**; main resolves it and refuses anything it doesn't recognize — no renderer-supplied filesystem path (avoids needless path-traversal surface even locally). Ghost nodes carry `ghost: true`; the renderer disables click-to-open on them (no read attempted).

- **One map, not two (L-1).** The absolute path lives **on the cached node object** in main's single graph cache (stripped from the position-free payload before IPC), and `read-note` resolves from that same cache — not a separate `id → path` map that could drift from the graph (node present in one, missing in the other). If a node was deleted between render and click, resolution simply fails and the read is refused.
- **Symlink containment on read (H3).** Resolving a node id to a cached path is **not** a containment check. Before reading, `fs.realpathSync(node.path)` and assert the result is inside `fs.realpathSync(NOTES_VAULT_DIR)` — refuse otherwise. Without this, a note `secret.md → ~/.ssh/id_rsa` (a symlink inside the vault) passes the `.md`/`isUserNote` filter, becomes a node, and `read-note` would follow the link and hand an arbitrary file to the renderer. The `read-note` handler also type/bound-checks its arg (`typeof id === 'string'`, length cap) since an XSS-in-renderer could pass anything (L1).
- **Symlinks in scan/watch (H3).** `fs.watch({recursive:true})` (FSEvents) does not reliably deliver events behind symlinked subtrees, and a recursive `readdir` can loop on a symlink cycle. Resolve `realpath` before watching, and skip symlinked directories during scan (or track visited inodes); a symlinked vault gets rescan-on-open freshness only.

### D9 — Untrusted-content hardening (notes may originate from the web)

Unlike the task reader (Claude-authored content), the galaxy renders **genuinely untrusted** local content: `wiki-ingest` pulls web articles/PDFs into the vault. This is a different threat from the canvas-MCP's deliberately right-sized *network* posture (which we do NOT re-open) — it is about not executing/leaking via note content in a privileged renderer (`contextIsolation: true`, `nodeIntegration: false`, but `window.iris` is exposed and there is **no CSP or navigation guard** in the app today).

- **Node-label tooltip XSS (H2).** `3d-force-graph`'s default `.nodeLabel()` assigns the accessor result to `innerHTML` in a `.graph-tooltip`. A note titled `<img src=x onerror=…>` would execute in the main world with full access to `window.iris`. **Do not feed raw text to the built-in HTML tooltip** — disable it and render labels via an escaped/sanitized path, or pass an HTML-escaping accessor. *(Verify the exact tooltip mechanism on the pinned `3d-force-graph` — lib not installed.)*
- **NoteReader markdown stays escaped.** `ReaderOverlay` uses `react-markdown` with `remark-gfm` only — **no `rehype-raw`, no `dangerouslySetInnerHTML`** — so raw HTML in a note is escaped. `NoteReader` MUST match this exactly; state it so a future edit can't regress it.
- **Navigation guard (M1).** There is no `will-navigate`/`setWindowOpenHandler` anywhere. `react-markdown` renders `[t](https://…)` as a real `<a>`; a click would top-level-navigate the single BrowserWindow to the remote page (the app is gone). Add app-wide `setWindowOpenHandler(() => ({action:'deny'}))` + a `will-navigate` handler that blocks anything but the dev/prod app URL and routes external links via `shell.openExternal`. Small, safe, and closes the hole this feature opens.
- **Escape hatch (L3).** While active, the fullscreen `.hud-hit` galaxy disables click-through, so it eats all desktop clicks. Wrap the galaxy in an **error boundary** that force-closes the layer on throw (WebGL context lost / lib error), and ensure **Esc force-closes** regardless of layer state — so a crashed layer can't trap the user behind an invisible click-blocker.
- **CSP (M2) — DECIDED: not in this change.** A Content-Security-Policy would be defense-in-depth against remote-resource beacons (`![x](https://…/p.gif)`) and script injection, but it is app-wide and must allowlist the MediaPipe CDN (gesture control fetches WASM+model at runtime), WebGL, and `data:` — real breakage risk to gesture/voice. The concrete injection/navigation holes are closed by H2/H3/M1/L1 without it, so **CSP is deferred to a dedicated app-wide security change** (user decision, 2026-07-24) rather than bundled into a "view the vault" feature. A remote image in a note can still load (a tracking beacon) until that change lands — accepted for now.

### Packaging / TCC / `file://` (verified — record so it isn't re-litigated)

- `~/iris-second-brain` sits **directly under home**, outside macOS TCC-protected folders (Desktop/Documents/Downloads/iCloud), so reading and `fs.watch`-ing it needs **no TCC prompt and no entitlement**, even under a future hardened-runtime signed build. If the vault path is ever moved under `~/Documents`, TCC would then apply — a reason to keep it where it is.
- `3d-force-graph` runs `d3-force-3d` on the renderer main thread with **no web worker, no WASM, no runtime CDN fetch**, so it has **none** of the `file://` asset footgun that forced Excalidraw's `EXCALIDRAW_ASSET_PATH` vendoring — do not over-engineer asset vendoring. (Only verify that node-label text sprites, if `three-spritetext` is used, don't pull a runtime font.)
- `gray-matter` must be a runtime **`dependency`** (it runs in main; a `devDependency` wouldn't be bundled by electron-builder — L4).

## Risks / Trade-offs

- **[Two `three` copies]** → D2: `resolve.dedupe` + `overrides.three` + `npm ls three` check; r3f-native fallback if a `three` major conflict can't be overridden.
- **[Layout reheats on every fs.watch fire]** → H2/M-B/D3: main pushes the **full position-free graph** each time; the renderer owns a stable `Map<id,node>`, reconciles in place, and actively manages motion (pin unchanged nodes / low alpha when topology is unchanged) — reused refs alone are not enough, `graphData()` resets the sim alpha.
- **[`UnrealBloomPass` may output opaque, killing the CSS backdrop]** → H-A/D4: spike the transparent-canvas + composer coexistence first; fall back to painting deep-space inside the graph scene or a composer-free sprite glow.
- **[A second `three` (stats-gl 0.170) already on disk]** → H-B/D2: `overrides.three` lands first (bumps stats-gl to 0.181, verify drei still works), then the single-copy gate.
- **[Malformed frontmatter blanks the galaxy]** → M-C: per-note try/catch, degrade to a tagless node.
- **[First-run vault has only wiki plumbing]** → H4/D3: exclusion list; empty-state keys on *user* notes.
- **[Large vault jank / GPU]** → position-preserving updates + debounce; CSS starfield (no extra GL context); pause the galaxy sim+render on the HUD `running` signal (L1); size guard/LOD deferred.
- **[fs.watch noise/misses]** → recursive watch + coarse debounce + rebuild-from-scan + try/catch.
- **[Case-insensitive resolution vs exact-case ids]** → M3: lowercased target map; document collision policy.
