## Context

`SetupPanel.tsx` already has a full device-selection pattern for the gesture camera: `SYSTEM_DEFAULT_CAMERA`, an `enumerateDevices()` + `devicechange`-driven `camDevices` list gated on `cam === "granted"`, a `cameraDeviceId` prop persisted to `localStorage` in `App.tsx`, and an `onChangeCameraDevice` callback. `useHandControl(enabled, deviceId)` picks up device changes via its effect's dependency array, so the camera stream restarts live when the selection changes.

Microphone capture is separate: `useAudioPipeline.startCapture()` calls `getUserMedia({ audio: { echoCancellation, noiseSuppression, autoGainControl, channelCount: 1 }, video: false })` with no device targeting, and is driven by `start()`/`stop()` from `App.tsx`'s session lifecycle rather than a `deviceId`-keyed effect.

**There is a second, independent mic consumer: `useWakeWord.ts`.** It runs its own `getUserMedia({ audio: { channelCount: 1, echoCancellation, noiseSuppression, autoGainControl }, video: false })` inside a `useEffect` keyed only on `[enabled]`, where `enabled = hasBridge && wakeWordEnabled && !sidecarRunning` (`App.tsx:420-426`). In other words: `useAudioPipeline` captures while a Gemini Live session is running; `useWakeWord` captures while idle and wake word is on. The two are temporally exclusive but both are "the microphone Iris listens through," and a device picker that only threads into `useAudioPipeline` would silently fail to apply the user's choice during wake-word listening — the exact scenario (a noisy default mic causing missed/false "Hey Iris" detections) that motivates picking a specific device in the first place. Both consumers are in scope for this change.

## Goals / Non-Goals

**Goals:**
- Let the user pick a specific mic input device from the Setup Panel, mirroring the camera selector's UI and persistence pattern.
- Apply a device change live to whichever mic consumer is currently active — `useAudioPipeline` during a session, `useWakeWord` while idle and armed — without disturbing the Gemini Live session when one is running.
- Keep working (fall back to System Default) if the selected device becomes invalid, rather than going silent, for either consumer.

**Non-Goals:**
- No Glass HUD or voice/tool-driven mic selection (Setup Panel only, same surface as the camera picker).
- No changes to audio encoding, sample rate, or the AudioWorklet downsampling path — only which physical/virtual device feeds the existing graph.
- No IPC or main-process changes; this stays entirely in `navigator.mediaDevices` renderer code, like the camera selector.

## Decisions

**Reuse the camera selector's UI/persistence shape, not a shared abstraction.** `SetupPanel.tsx` gets its own `micDeviceId`/`onChangeMicDevice` prop pair, its own `micDevices` state + `devicechange` effect (filtered to `audioinput`), and its own `MIC_STORAGE_KEY = "iris.micDeviceId"` in `App.tsx`, following the exact structure already used for `cameraDeviceId`. Extracting a shared `useDevicePicker` hook was considered but rejected: two call sites with slightly different failure semantics (see below) don't justify an abstraction, and the existing code already accepts this duplication between camera and (now) mic.

**Hot-swap via explicit stop/start, not an effect dependency array.** Unlike `useHandControl`, which restarts implicitly because its `useEffect` depends on `deviceId`, `useAudioPipeline` exposes imperative `start()`/`stop()` tied to the Gemini session lifecycle, not to `deviceId`. `App.tsx` will call `audio.stop()` followed by `audio.start()` (or an equivalent `restartCapture()` exposed from the hook) when `micDeviceId` changes while a session is running, rather than reshaping `useAudioPipeline` around a dependency-array effect. This keeps the hook's imperative API intact and avoids restarting playback (`stop()`/`start()` here must only affect capture, not the output context — `stopCapture()`/`startCapture()` already split this correctly internally; the exposed restart path calls those two directly rather than the full session `stop()`/`start()` which also touches playback).

**Hot-swap must re-apply the current `muted` state to the freshly acquired stream — this is a real, privacy-relevant gap, not a hypothetical.** `toggleMute()` only ever mutates `track.enabled` on `inputStreamRef.current`'s *existing* tracks; it does not touch anything that `startCapture()` reads. `stopCapture()` never references `muted`/`setMuted` at all — only the *full* `stop()` does (`setMuted(false)`, intentionally, since a brand-new session is expected to start unmuted). Because the hot-swap path deliberately calls `stopCapture()`/`startCapture()` directly rather than the full `stop()`/`start()` (precisely to avoid resetting `sessionStartRef` and touching playback, per the decision above), a muted user who switches microphone mid-conversation would otherwise end up with `audio.muted` still `true` (mute button still shows muted) while the newly acquired `MediaStream`'s tracks default to `enabled: true` — Iris silently resumes sending their audio despite the UI claiming they're still muted. `startCapture()`/`restartCapture()` SHALL apply the current `muted` state to every audio track on the newly acquired stream (`track.enabled = !muted`) before wiring it into the capture graph, exactly mirroring `toggleMute()`'s own assignment.

**Mic auto-falls-back on device failure; camera does not — this is intentional, not an inconsistency.** The camera selector's spec (`setup-panel`) explicitly marks a missing saved device as "unavailable" without switching away from it, because a missing camera has no functional cost (gesture control is optional and already off). A missing/failed mic is not optional — silence breaks the core product (voice conversation), so `startCapture()` catches the `getUserMedia` rejection for a specific `deviceId`, retries once with no `deviceId` constraint (System Default), and on success updates both the persisted value and the visible selection so the UI stays truthful about what's actually active. This mirrors the existing pattern in the same function where an `AudioWorklet` load failure already logs via `onLog` and cleans up — the new fallback reuses that logging path rather than introducing a new error-reporting mechanism.

**Constraint construction is one pure module in `src/lib/`, unit-tested — not a copy inside each hook.** This reverses an earlier draft of this design, which proposed a private `audioConstraintsFor` inside each of the two hooks. The repo already has an established convention that this change must follow rather than re-invent: pure logic lives in `src/lib/*.ts` with a colocated `*.test.ts` run by `npm test` (vitest), and the closest precedent is literally from this same audio pipeline — `src/lib/downsample.ts` + `src/lib/downsample.test.ts` were extracted out of the mic path for exactly this reason, alongside `hand.ts`/`hand.test.ts` and `tasks.ts`/`tasks.test.ts`. The `test-harness` living spec requires the runner to exist and requires tests to run with none of Iris's runtime prerequisites — constraint-building is pure object manipulation, so it qualifies cleanly (no `AudioContext`, no `getUserMedia`, no Electron).

So: a new `src/lib/mic-device.ts` exports `SYSTEM_DEFAULT_MIC` and `micConstraints(base, deviceId)`, which returns `base` when `deviceId` is empty or the System Default sentinel, and `{ ...base, deviceId: { exact: deviceId } }` otherwise. **It takes the base constraints as a parameter rather than hardcoding them**, because the two consumers' base sets legitimately differ and are about to differ more: `useAudioPipeline` uses `autoGainControl: true`, while the sibling `harden-wake-word-detection` change deliberately sets `autoGainControl: false` on the wake-word stream so ambient noise is not amplified into the model's sensitive range. A helper that hardcoded one base set would either break that change or silently undo it.

This also fixes a duplication smell the earlier draft would have propagated: the camera sentinel is currently declared **twice** — exported from `useHandControl.ts:78` and re-declared as a local `const` in `SetupPanel.tsx:31`. Putting `SYSTEM_DEFAULT_MIC` in `src/lib/mic-device.ts` gives all four mic call sites (`useAudioPipeline`, `useWakeWord`, `SetupPanel`, `App.tsx`) one import instead of repeating the string literal, and removes the "two implementations drift apart" risk this design previously had to list as an accepted trade-off.

**`muted` must be read through a ref after the `await`, not from the render closure.** `startCapture()` awaits `getUserMedia` (and the worklet `addModule`) before it can apply mute state to the new tracks. `muted` is `useState`, so the value visible inside that async continuation is the one captured when `startCapture` was called — if the user toggles mute during the acquisition window, the freshly-wired stream gets the stale value and the indicator desyncs again, reintroducing the bug in a narrower window. The fix follows a pattern already used throughout this codebase (`inputLevelRef`/`outputLevelRef` here, `onWakeRef.current = onWake` in `useWakeWord.ts`): keep a `mutedRef` written by `toggleMute` alongside `setMuted`, and have `startCapture` read `mutedRef.current` *after* its awaits, immediately before wiring the stream in.

**`useWakeWord` hot-swaps via its existing effect dependency array, not an imperative restart.** Unlike `useAudioPipeline`, `useWakeWord`'s entire capture/inference graph already lives inside one `useEffect` keyed on `[enabled]`, and fully tears down and re-initializes on every `enabled` transition (this is how arm/disarm already works). Adding `deviceId` to that dependency array (`[enabled, deviceId]`) gets a live device-swap for free, exactly the way `useHandControl`'s `[enabled, deviceId]` effect already hot-swaps the camera — no new imperative API needed on this hook. This is the opposite mechanism from `useAudioPipeline` (imperative `restartCapture`) because the two hooks have different existing shapes; forcing them to match would mean a larger, unrelated refactor of one of them.

**This "teardown on `deviceId` change" decision must stay narrowly scoped to `deviceId` alone, not to `useWakeWord`'s settings in general — see the sibling change below.** A concurrently open, equally unimplemented OpenSpec change, `harden-wake-word-detection`, adds sensitivity settings (`threshold`, `consecutive`) to this same hook and deliberately threads them through a ref rather than the effect's dependency array, precisely to avoid tearing down and re-acquiring the microphone on every settings save (its task 3.2: "not by adding them to the effect's dependency array, which would tear down and re-acquire the microphone"). That principle and this change's `[enabled, deviceId]` decision are **not actually in conflict**: a sensitivity threshold is a pure JS comparison value that never requires a new `MediaStream`, so it correctly avoids the dependency array; a device id fundamentally cannot be applied to an already-open stream — the browser requires a fresh `getUserMedia` call against the new device — so it correctly belongs in the dependency array. Whoever implements either change should keep these on separate footing: `deviceId` triggers full teardown/re-init, sensitivity settings must not. Implemented naively without this distinction (e.g. "just add everything new to a settings ref to be safe"), a device change would silently keep capturing from the old device.

**Sequencing: three unimplemented changes converge on the same two files. Recommended order is wake-word-hardening → security-boundaries → this change, and this change should be implemented last.**

At the time of writing, all three of these changes have 4/4 planning artifacts complete and **zero** implementation tasks done:

| Change | Touches `useWakeWord.ts` | Touches `SetupPanel.tsx` | Touches `setup-panel` spec |
| --- | --- | --- | --- |
| `harden-wake-word-detection` | signature (`onError` → `onLog(level, message)`), constraints (`autoGainControl: false`), ref-threaded sensitivity settings | adds a sensitivity control by the wake-word toggle | yes — same `MODIFIED` requirement block |
| `harden-security-boundaries` | vendored asset paths (replacing the jsDelivr/`storage.googleapis.com` URLs) | Gemini key field renders empty + stored-key test path | (its own deltas) |
| `microphone-device-selection` (this) | adds `deviceId` param + dependency array, constraints | adds a device selector under the Microphone permission row | yes — same `MODIFIED` requirement block |

Recommending this change go **last** is not just conflict-avoidance, it is a risk ordering:

- `harden-wake-word-detection` fixes a live, user-visible defect (Iris waking unprompted) — a bug fix outranks a feature, and it is the change that *settles* `useWakeWord`'s signature and constraint set. Landing it first collapses this change's task-2 branching ("if the sibling landed, use `onLog`; otherwise `onError`") into a single known state, and means the shared `micConstraints(base, deviceId)` helper is written against final base constraints rather than ones about to change underneath it.
- It is also the change carrying new tests and two spec deltas, so it is the most expensive of the three to rebase. Rebasing should fall on the cheapest change, which is this one.
- `harden-security-boundaries` touching the same hook's asset URLs is orthogonal to both device selection and detection tuning, so it can slot anywhere; putting it second keeps this change's rebase to a single, already-stabilized file.

Mechanically, on the spec side: OpenSpec archiving diffs a change's delta against the **current** living spec, so whichever change archives first lands cleanly and each later one must re-base its `specs/setup-panel/spec.md` delta against the by-then-updated `openspec/specs/setup-panel/spec.md` — otherwise its archive silently drops the earlier change's addition to that same requirement block. This change's `setup-panel` delta was written against the pre-sibling living spec and **will** need that re-base if it goes last as recommended; task 5.3 is the checkpoint for it.

**This sequencing is a recommendation, not a constraint this change can enforce.** If the priority call is to ship the mic picker first instead, that is workable — but then the other two changes inherit the rebase, and this change's task group 2 must be implemented against `useWakeWord`'s *current* (`onError`, `autoGainControl: true`) shape, with the sibling change's own tasks updated to expect a `deviceId` parameter and dependency array that already exist.

**Device-fallback reporting is a return value, not a callback.** Task-list precision matters here: `startCapture()`/`start()`/`restartCapture()` (in `useAudioPipeline`) and `useWakeWord`'s `init()` all resolve/settle at a well-defined point already awaited by their caller (`App.tsx`'s `start()` `await`s `audio.start()`; the effect in `useWakeWord` doesn't need to report outward, it can update its own local persisted state directly since it owns `deviceId` symmetrically with `useHandControl`). Rather than adding a new `onDeviceFallback` callback prop (a second, easy-to-forget channel alongside `onLog`), `useAudioPipeline`'s `start()`/`restartCapture()` SHALL return the actually-active device id (which may differ from the requested one after a fallback), and `App.tsx` reconciles persisted/displayed state from that single return value. This avoids an event-ordering ambiguity between "log fired" and "callback fired" that a second channel would introduce.

**Overlapping start/restart calls need an epoch guard, mirroring the existing `flushEpochRef` pattern — and without it the failure mode is a hot-mic leak, not just a confused ref.** `startCapture()`'s existing re-entrancy guard is `if (typeof window.iris === "undefined" || inputContextRef.current) return;`, but `inputContextRef.current` is only assigned on the **last** lines of the function, after `await getUserMedia` and after `await context.audioWorklet.addModule`. So the guard does not actually serialize concurrent calls: two `startCapture()` invocations overlapping in that acquisition window both pass the check, both open a `MediaStream`, and the second one to finish overwrites `inputStreamRef`/`inputContextRef` — leaving the first stream with **no reference anywhere and its tracks never stopped**. On macOS that means the microphone stays open and the OS recording indicator stays lit for the life of the process, with audio still being captured from a device the user thinks they switched away from. This is a pre-existing latent bug (today only two racing session starts could trigger it, which the UI makes hard to do); adding a user-facing control that calls into this path on every selection change makes it reachable, so this change must fix it rather than inherit it.

`useAudioPipeline` already solves the analogous problem for playback (`flushEpochRef`, checked in `playGeminiAudio` before `source.start`). `startCapture()`/`restartCapture()` SHALL apply the same pattern: increment an epoch at call entry, and if the epoch has advanced by the time acquisition resolves (success **or** fallback retry), stop the just-opened tracks and close the just-opened context instead of assigning them to the live refs.

**The selection persists in `localStorage`, not `.env`, and that asymmetry with the sibling change is deliberate.** After both changes land, wake-word *sensitivity* will live in `.env` (via `ALLOWED_CONFIG_KEYS`, hand-editable, exposed through the config IPC) while the wake-word *device* lives in `localStorage`. That looks inconsistent, so record why it is correct: `MediaDeviceInfo.deviceId` values are opaque, machine-specific, and origin-scoped — they are not portable between machines, not meaningful to a human hand-editing a config file, and can be invalidated by the browser. Putting one in `.env` would invite a user to copy a config between machines and get a dangling device id, which is exactly the failure the auto-fallback requirement exists to paper over. `localStorage` is also what the existing camera selection already uses (`iris.cameraDeviceId`), so device choices stay in one mechanism and hand-editable settings stay in the other. A future reviewer should not "unify" these without reading this paragraph.

## Risks / Trade-offs

- **Retry-on-failure could mask a real problem (e.g., permission silently revoked mid-session) as a device issue.** → The `onLog("error", ...)` call on fallback states plainly that the previously selected device failed and Iris reverted to System Default, so the user sees it in the Work Stream/log rather than the app just quietly using a different device forever.
- **Hot-swap briefly drops the mic input (teardown + rebuild of the AudioContext/worklet).** → Same brief gap already exists today whenever a session stops and restarts; this is not a new failure mode, just a new trigger for an existing one.
- **Duplicating the camera picker's *selector UI* in `SetupPanel.tsx` grows the file (~900 lines) rather than shrinking it.** → Accepted: the JSX/enumeration-effect duplication stays (a shared picker component is deferred until a third device type appears), but the *pure* part — sentinel + constraint building — is extracted to `src/lib/mic-device.ts` per the decision above, so the duplication is confined to presentation.
- **Forgetting `useWakeWord` and only wiring `useAudioPipeline` would ship a half-working feature.** → Both consumers are explicit goals and explicit spec requirements/tasks in this change; `useWakeWord`'s independent `getUserMedia` call was easy to miss because it lives in a different file from the Setup Panel/camera pattern this change otherwise mirrors closely.
- **Two independent fallback/retry implementations (`useAudioPipeline`, `useWakeWord`) could still drift, since only constraint-building is shared and the retry/report logic is not.** → Partially mitigated by `src/lib/mic-device.ts` owning the sentinel and constraint shape, so the two paths cannot disagree about *what* System Default means. The retry-once-and-report behavior remains duplicated because the two hooks report through different channels (a return value vs. the hook's log callback) and have different teardown shapes; unifying that would require restructuring one of the hooks, which is out of scope. The spec pins the observable behavior for both so a drift becomes a spec violation rather than a silent inconsistency.
- **This change's own review history is a risk signal worth heeding.** → Three successive review passes each found a defect the previous had missed (missing `useWakeWord` consumer; mute-state desync on hot-swap; violating the repo's `src/lib/` + `npm test` convention while CLAUDE.md actively misstated that no test runner exists). The area is deceptively subtle: it is renderer-only and superficially a copy of the camera picker, but it sits on live `MediaStream` lifecycle, mute semantics, and OS-level device state. Implementation should lean on the unit test for the pure part and on the manual verification matrix in tasks group 5 for the rest, rather than assuming parity with the camera path.
