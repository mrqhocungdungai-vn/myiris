## Context

See proposal.md — Why. What matters for the approach:

- Hand-gesture tracking (`src/hooks/useHandControl.ts`) already runs MediaPipe **Tasks Vision** (`@mediapipe/tasks-vision@^0.10.35`, confirmed in `package.json`/`docs/REFERENCE.md`) as `GestureRecognizer`, opening `getUserMedia` into a hidden `<video>` element and running a `requestAnimationFrame` loop calling `recognizeForVideo`. The same package exports `FaceLandmarker`, a sibling task with the *same* `FilesetResolver`/WASM fileset — no new npm dependency.
- **Two** components render a visible `<video>` fed by that returned `stream`: `CameraDock.tsx` (deck mode) and `HudCamera` inside `HudShell.tsx` (HUD mode), mutually exclusive via `uiMode === "hud" ? <HudShell/> : <deck/>` in `App.tsx`. Both use the same `.camera-frame` markup, and `HudShell` already imports `HandSkeleton` from `CameraDock` to overlay both. A second tracking task must reuse the same live `MediaStream` — never a second `getUserMedia` — but should not attach to either component's video element; see D3.
- `HandSkeleton` (in the same file) establishes the **update** pattern this capability should follow: shapes positioned via a `requestAnimationFrame` loop writing DOM attributes directly through refs — never through React state — so a moving subject never triggers a 60fps re-render. `useHandControl`'s `HandState` models this with a dual `{ state, stateRef }`: `state` (React) is published only when a semantically meaningful field changes (`semanticEquals`); `stateRef` is updated every frame for the imperative reader.
- `HandSkeleton`'s **coordinate space**, however, is `viewBox="0 0 100 100"` with `preserveAspectRatio="none"` inside a `.camera-frame` that CSS pins to `aspect-ratio: 4 / 3` (`deck.css` for the deck, `hud.css` for HUD mode) — so that space is **anisotropic**: one x-unit is 4/3 the pixels of one y-unit. Harmless for a skeleton of lines and tiny dots (and `vector-effect: non-scaling-stroke` keeps its stroke widths right), but **this capability must not inherit it** — see D10. It is the reason circles and text need their own container here.
- `scripts/vendor-runtime-assets.mjs` downloads `gesture_recognizer.task` once (skip-if-present) into `public/runtime/mediapipe/`, plus the shared WASM glue — run via `postinstall` and before `vite build`. `renderer-content-security` requires this: the renderer must never fetch executable code (or, by the same reasoning applied here, a model asset) from a third-party origin at runtime.
- Confirmed via the installed package's own `FaceLandmarker.FACE_LANDMARKS_LEFT_IRIS` / `_RIGHT_IRIS` static connection constants (not assumed from memory): the 478-point face mesh's iris indices are **473** (left iris center) + **474–477** (left iris boundary ring) and **468** (right iris center) + **469–472** (right iris boundary ring). "Left"/"right" here are MediaPipe's own anatomical labels; treat them only as two stable per-frame identifiers, never as user-facing labels — see D5 on why they read opposite to what is on screen.
- `tokens.css` already defines `--cyan-rgb` (the app's default accent), `--amber-rgb`, and `--coral-rgb` — the "warning" palette this capability needs is not new.
- `deck.css` (upstream-verbatim; must stay byte-identical) already defines `@keyframes orb-spin` / `orb-spin-rev` (`to { transform: rotate(360deg) }` / `rotate(-360deg)`, no baked-in duration) for the main orb, and `@keyframes pulse-dot` (opacity 1 ↔ 0.45). Both are reusable as-is for this capability's rotations/pulses; new rules for this capability belong in `claude.css`, per the existing split.

## Goals / Non-Goals

**Goals:**

- Pin down, as an implementable spec, the properties that make an Iron Man / J.A.R.V.I.S.-style HUD read correctly — the ones that are invisible in any still image of the reference and that a reasonable implementation loses without noticing (identical treatment on both eyes reads as redundant; a 1:1-scaled ring is too small to see its own motion; solid rings don't appear to rotate; harmonic periods collapse the stack into one rigid spin; an untethered offset panel reads as a floating widget).
- Document the pitfalls in this codebase's existing overlay conventions that a straightforward implementation walks into — generally enough to prevent recurrence in *future* additions to this HUD, not only in the specific element where each was first identified.

**Non-Goals:**

- Wiring the placeholder telemetry panel to any real signal (heart rate, focus, temperature, or anything else). It stays illustrative until a later change explicitly takes that on.
- Any interaction, gesture, or app behavior derived from eye position. This is unambiguously decorative — see the spec's first requirement.
- Prescribing pixel-exact constants (ring radii, stroke widths, boost multipliers, layer counts, exact rotation periods) as immutable. The concrete numbers in D6's layer table are this design's first guesses — a starting point to re-tune by eye against a real camera, not a pixel-for-pixel contract.

  **What *is* contractual is the set of relationships between them**, because those are what produce the look and are invisible in a table of numbers: alternating direction between *adjacent* rotating layers, pairwise-distinct and non-harmonic periods, an asymmetric interruption on every rotating layer, at least one static layer as a reference, stroke-only rendering, and a ring visibly larger than the iris. The spec states those; it does not state radii.
- Reconciling this with `personal-knowledge-notes`/`second-brain-*` or any other capability — this touches only the Camera/Gesture dock.

## Decisions

### D1. `FaceLandmarker`, not a second/different face-tracking library

`@mediapipe/tasks-vision` already ships `FaceLandmarker` as a sibling to the installed `GestureRecognizer`. Using it costs zero new dependencies, reuses the exact same `FilesetResolver`/WASM fileset the hand tracking already vendors, and only needs one new model asset. The alternative (a dedicated eye-tracking library) would duplicate an already-solved WASM-vendoring problem for no benefit — this HUD needs iris position/size only, which `FaceLandmarker` provides without the blendshape or facial-transformation-matrix outputs (both left off — `outputFaceBlendshapes`/`outputFacialTransformationMatrixes` default false, and the plain `face_landmarker.task` variant, not the `_with_blendshapes` one, is what's vendored).

### D2. A second hook, not a second task bolted onto `useHandControl`

`useEyeTracking` is its own hook, mirroring `useHandControl`'s `{ state, stateRef }` shape exactly, rather than extending `useHandControl` to also run `FaceLandmarker` in the same loop. Hand-gesture tracking is a functional input device; this is decoration. Folding them into one hook/file would blur that distinction and push the file past a single responsibility — `useHandControl.ts` is already 324 lines, near the top of the 250–450 band, so a second inference task and its state would put it over. The two hooks run independent `requestAnimationFrame` loops against their own `<video>` elements fed by one shared `MediaStream` (D3) — each task reads the current frame independently; neither mutates it.

### D3. Take the shared `MediaStream` and own a detached `<video>` — not any surface's video ref

`useEyeTracking(stream, enabled)` takes the `MediaStream` that `useHandControl` already returns, creates its **own detached `<video>`** (`document.createElement("video")`, never mounted) as its detection source, and runs `FaceLandmarker` against that. No new `getUserMedia`: the one camera session is shared, which is what the spec's requirement is actually about — not which video element is used.

This copies `useHandControl`'s own structure exactly: it creates a detached `<video>` at line 128 of `useHandControl.ts`, keeps it private, and exposes `{ state, stateRef, error, stream }`. `useEyeTracking` is the same shape with the capture step removed.

**The rejected alternative was to take a video ref from the component that owns the visible preview** (originally `CameraDock`'s). Two surfaces render a camera preview — `CameraDock` in deck mode and `HudCamera` inside `HudShell.tsx` in HUD mode (D12) — each owning its own `<video>` and its own `srcObject = stream` assignment. Attaching to a component's ref therefore means:

- the hook is called from two places instead of one, and
- because the two surfaces are mutually exclusive (`uiMode === "hud" ? <HudShell/> : <deck/>` in `App.tsx`), switching modes **unmounts the camera component and so tears down and re-creates the `FaceLandmarker`** — a WASM/model re-initialization on every mode toggle, for no reason.

Owning a detached video instead makes the hook surface-agnostic: it is called once at the `App` level beside `useHandControl`, it survives mode switches untouched, and both surfaces' overlays become pure presentation receiving `{ eye, eyeRef }` props — exactly how `HandSkeleton` already receives `{ hands, handsRef }` in both surfaces today.

### D4. Dual `{state, stateRef}`, mirrored-x, and presence-gated publish — copied from `useHandControl`

Same rationale as the existing hook: continuous per-frame data (position, radius) only needs to reach an imperative rAF reader, never React; only *presence* transitions (a face appearing/disappearing) need to trigger a re-render, so mount/unmount decisions stay correct without paying for 60fps re-renders. `x` is mirrored (`1 - x`) for the same reason `useHandControl` mirrors hand landmarks: the preview `<video>` is CSS-mirrored (`transform: scaleX(-1)`) for a natural selfie view, and overlay coordinates must be mirrored to match rather than the CSS compensating for raw coordinates. That rule is written `.camera-frame video` in `deck.css`, and **both** surfaces use `.camera-frame`, so one mirroring applies everywhere — there is no per-surface case to handle.

### D5. Asymmetric per-eye rendering: one ring, one panel — not two of either

The obvious implementation — the same small ring on both eyes — reads as redundant rather than as symmetric, and at typical webcam-eye scale (roughly 10–20px) a literal 1:1-scaled ring is too small to show its own rotation at all. The equally tempting escape from that (docking the second element to a fixed corner of the frame, magnifier-style, where there is room for it) is worse: it stops being eye tracking and reads as unrelated chrome that happens to share a panel. So **both elements track their own eye's live position every frame** — that is non-negotiable — but they are visually distinct instruments:

- One eye drives the ring HUD, deliberately drawn **larger than the true iris** (a `EYE_RING_VISIBILITY_BOOST` multiplier applied to the group's scale, on top of the iris radius) — a 1:1 scale was tried and read as too small to see the accent arc spin.
- The other eye positions the placeholder panel, **offset to the side** of that eye by a fixed fraction of the frame's width, so it never overlaps the eye it's attached to.

The assignment this design specifies: the ring is driven by `eyes[EYE_RING]` (MediaPipe's "right" eye) and the panel by `eyes[EYE_READOUT]` ("left"). The spec fixes it in on-screen terms — *ring right, panel left* — and this is the landmark pairing that produces it; either way it must be *fixed and consistent*, never varying frame-to-frame or session-to-session.

**State the assignment in on-screen terms as well as landmark terms.** The `<video>` is CSS-mirrored (`transform: scaleX(-1)`, `deck.css`) and coordinates are mirrored to match (D4) — which is what makes the preview read as a *mirror*: the subject's own left eye appears on the **left** of the displayed frame, and their right eye on the right. So here the two vocabularies happen to agree, and that is worth writing down precisely because it is the kind of thing assumed rather than checked: an earlier draft of this document asserted the opposite (anatomically-"left" appearing on screen-right) and the implementation silently inverted its landmark indices to keep the on-screen result it was actually aiming for. Anyone verifying this feature reads it off the screen, not off a landmark index. For the assignment above: *ring on the right of the screen, panel on the left of the screen.*

### D6. Multi-ring, multi-color, alternating rotation — the "lock-on" identity

Requested explicitly, in these terms, after the first (single-tone-cyan) pass read as "not dangerous enough" and a later request asked for it to look more like the reference — an **Iron Man / J.A.R.V.I.S. targeting reticle**, not this app's usual calm cyan chrome: red/coral (`--coral-rgb`) and orange/amber (`--amber-rgb`) alongside the app's default cyan, across several concentric ring elements rotating at different speeds *and* in alternating directions (not all the same way), deliberately reading as an alert/lock-on instrument rather than the calm single-tone cyan used everywhere else in the app's chrome (hand skeleton, orb, HUD shell).

**The reference layer stack.** Radii are expressed as a fraction of the bezel radius `R`, so the whole assembly scales with the tracked iris (per D5's boost) as one unit. Outward to inward:

| Layer | Element | r (×R) | Stroke | Color | Motion |
| --- | --- | --- | --- | --- | --- |
| L0 | Wing brackets / chevrons flanking left + right | 1.30 | 2 | coral | static |
| L1 | 24-tick graduated dial, long ticks every 90° | 1.06–1.18 | 1 | alternating coral/amber | static |
| L2 | Segmented ring — 3 **unequal** arcs with gaps | 1.00 | 1 | cyan | CW, 12s |
| L3 | Solid bezel — the dial's fixed anchor | 0.92 | 2.5 | coral | static |
| L4 | Dashed ring | 0.78 | 1 | coral | CCW, 7s |
| L5 | Accent sweep arc (~110°, fading gradient) + 2 marker dots riding it | 0.62 | 3 | amber gradient | CW, 3.2s — see D7 |
| L6 | Dashed ring | 0.46 | 1 | amber | CCW, 5s |
| L7 | Center crosshair: 4 short radial ticks + a dot, pulsing opacity | 0.10–0.22 | 1 | cyan | static |

The 24-tick dial's coral/amber alternation is a "hazard stripe" that falls out of the existing long/short tick alternation for free, needing no separate color logic.

**Three motion laws — this is the part that produces the reference look, and the part a rewrite is most likely to lose.** The layer table above is tuned geometry (see Non-Goals); these three properties are not, and the spec states them as requirements:

1. **Every rotating layer carries an asymmetric interruption** — an unequal gap, a dash pattern, an open arc. A uniform continuous circle that rotates is visually indistinguishable from a static one, so it contributes motion the viewer cannot perceive while still costing a compositing layer. This is the actual reason the rings are dashed/segmented rather than solid; it is not decoration.
2. **Adjacent rotating layers turn in opposite directions.** The shear that reads as "many independent instruments" is only legible between layers the eye can compare side by side. Alternating merely *somewhere* in the stack (e.g. outermost CW, innermost CCW, everything between one way) loses the effect entirely — hence L2 CW / L4 CCW / L5 CW / L6 CCW.
3. **Periods are pairwise distinct and not integer multiples of one another** (12 / 7 / 3.2 / 5 s). Harmonically related periods re-synchronize on a fixed cycle, and at each re-sync the whole stack momentarily reads as one rigid spinning image rather than as several separate dials — the single most damaging failure mode for this look, and an easy one to introduce by picking round numbers.

**Two supporting constraints, same origin:** every layer is **stroke-only with additive glow** (no fills — fills read as solid discs and kill the instrument-panel feel), and **at least one layer stays static** (L1's dial + L3's bezel). Without a fixed reference the eye has nothing to measure the rotations against, and the whole assembly reads as undifferentiated noise instead of moving parts.

### D7. The partial-arc rotation pivot bug, and why it isn't a CSS `transform-origin` problem

This is the one piece of this design worth treating as load-bearing rather than cosmetic, because it will recur if not stated as a constraint.

CSS `transform-box: fill-box; transform-origin: center` rotates an element around the center of *its own bounding box*. For a full circle centered on the group's local origin (the tracked eye's center, post-translate), that bounding box **is** centered on the origin — so this works correctly for every full-ring element in this design (the cyan/coral/amber rings above), with no imperative code needed.

It does **not** work for the accent arc, because a partial arc's bounding box only spans the wedge it actually sweeps — it is not centered on the circle it belongs to. Rotating it via `transform-origin: center` under `fill-box` pivots around that off-center bounding-box centroid, which reads as a visible wobble/orbit rather than a clean spin in place. (The alternative default, `transform-box: view-box`, is worse here: it anchors percentages to the nearest `<svg>`'s viewBox, which after this HUD's `translate(...)`-based positioning is an entirely different point from the tracked eye's center.)

The fix: rotate the arc (and anything that must move with it, e.g. small marker dots along its sweep) via an **explicit SVG `rotate(deg)`** attribute, written imperatively every frame alongside the group's translate/scale — SVG's single-argument `rotate()` unambiguously pivots around the local coordinate system's origin `(0, 0)`, which *is* the tracked eye's center by construction, with no bounding-box ambiguity at all. This requires the arc (and anything riding with it) to sit in its own child group, separate from the full-ring elements that *can* safely use the CSS approach.

**Anything added to this HUD later that sweeps only part of a circle inherits this same constraint** — it is not specific to this one arc.

### D8. An "acquire" transition when a face is first detected — and why it cannot be a CSS transition

A presence-gated overlay appears at full size the frame a face is detected and vanishes the frame it is lost — which is what the requirements above literally ask for, and which reads as a sprite toggling rather than as an instrument locking on. The reference behavior is an **acquire**: on the presence transition from no-face to face, the ring converges — it appears at a noticeably larger scale and eases inward to its tracked size over a few hundred milliseconds (roughly 250–400ms), settling with a brief overshoot/settle beat rather than a linear stop. Loss of the face is the plain inverse or a simple fade; only acquisition is dramatized, because that is the moment being narrated.

**The implementation constraint that makes this a design decision rather than a styling detail:** the ring group's `transform` is rewritten imperatively **every frame** by the rAF loop (translate to the tracked eye, scale by the boosted iris radius — D4/D5). A CSS `transition` or `@keyframes` animation on that same group's transform is therefore cancelled on every frame, and produces either nothing or a visible stutter. The acquire must instead be driven **inside the per-frame write**: hold the acquisition timestamp, derive an eased progress factor from elapsed time, and multiply it into the scale the loop is already writing. This is the same class of mistake as D7 — reaching for a declarative CSS mechanism on an element whose transform is under imperative per-frame control — and worth stating once so both are recognized as instances of one rule.

The per-layer rotations are *not* affected: they live on child elements whose own transforms CSS owns exclusively (D7), so they animate declaratively as normal while the parent group is imperatively driven.

### D9. The panel is a tethered callout with a deliberately absent frame — not a card

"An angular panel with cut corners" is the obvious reading of the brief, and it lands on a generic UI card rather than on the reference. Four properties separate a J.A.R.V.I.S.-style readout from a styled box, and each is worth stating because each is individually easy to drop:

**The frame is mostly absent.** Corner brackets (L-shaped, at the corners only) with **no closed outline** — the panel's edges are implied by its corners and by the alignment of its own text, not drawn. A rectangle with a border reads as chrome from any other application; the missing edges are what make it read as an overlay projected onto a scene. One corner is chamfered rather than all four, so the shape has an orientation. The background is a translucent dark wash, never opaque: the camera image stays visible through it, which is what keeps it reading as a *projection over* the video rather than a *panel occluding* it.

**A tether connects it to its eye, and this is the load-bearing part.** An elbow polyline: a small dot at the tracked eye's center, a short diagonal run outward, a horizontal run across to the panel, terminating in a short tick against the panel's near edge. Without a tether an offset panel is a widget that happens to sit near a face; with one it is a callout on a target — this is the single largest contributor to the reference look, and the thing a correctly-tracked but unconnected panel is still missing. **Both ends move every frame** (the eye end from tracking, the panel end because the panel is positioned off the eye), so the tether is recomputed per frame like everything else here — it cannot be a static shape parented to either end.

**The readout churns.** Values update continuously at a visible but unhurried cadence; a static readout reads as a screenshot pasted over the video no matter how well it is styled. This *supports* rather than undermines the placeholder requirement — visibly churning digits are self-evidently not a measurement. Two constraints come with it: the value column is right-aligned with tabular/fixed-advance figures, so a changing digit count never reflows the row (a readout whose layout twitches reads as broken, not as live), and at least one row is a **segmented** bar meter — discrete cells, not a smooth fill, since a smooth progress bar is the most recognizably-generic-UI element available. The panel should be denser than it is readable: more rows and tokens than a viewer can take in at a glance, which is what makes it read as instrumentation rather than as a label.

**The two-tone division is semantic.** The ring is coral/amber — alert, alarm, lock-on. The panel is informational cyan with amber reserved for a single accent value. This is not "two elements that happen to differ" (which is all the earlier draft asked for): the reticle is the thing raising an alarm, the panel is the thing reporting, and the palette says which is which. A header strip with an inverted/brighter label plus a status token, and a periodic scan-line sweep down the panel, complete it.

**Sequencing with D8's acquire:** the panel arrives *after* the ring locks, not with it — the tether draws outward first, then the panel unfolds at its end. The stagger states the causality (target acquired, therefore readout) and is a few hundred milliseconds of work for most of what makes the moment read as deliberate.

**The panel is pinned left of its eye, and clipping is the accepted cost.** `.camera-frame` is `overflow: hidden`, so a fixed one-sided offset means the panel is sliced whenever the tracked eye approaches that edge — which happens the first time anyone turns their head, not in some edge case. An earlier version of this design escaped that by flipping the panel to its eye's other side, with a hysteresis deadband so it would not strobe at the threshold. **That was built and it is wrong on both counts.**

The near objection is geometric: each eye owns one half of the frame — that is what the asymmetric assignment (D5) buys — and the flipped position is inside the *other* eye's half, where the ring is. A rule whose purpose is to keep the panel from being clipped by the frame instead sends it into a collision with the reticle.

The far objection is that the deadband was solving the wrong problem. The panel jumping was never really about strobing at one threshold; it was about a position that depends on head pose at all. Hysteresis only chooses *when* a discontinuity fires — it cannot make one stop reading as a malfunction, and a viewer who sees the readout leap across a face does not care that it did so no more than once per second.

So: `anchorX = eyeX - offset`, unconditionally, with no frame-bounds term and no carried state. When the eye nears the frame's left edge, the panel is clipped and part of it is lost. That is acceptable in a way neither alternative is, and specifically because the content is placeholder telemetry (D9) — there is no information in it to lose. The layout function keeps a mutable `layout` object only for the reveal stagger now, not for a side that has to persist across frames.

### D10. The tracked overlays need an isotropic coordinate space — and text needs to leave SVG entirely

The existing overlay is `viewBox="0 0 100 100"` + `preserveAspectRatio="none"` in a `4 / 3` frame (see Context). In that space one x-unit is 4/3 the pixels of one y-unit, so **a `<circle>` renders as an ellipse stretched 33% horizontally and `<text>` renders 33% wider than it should be**. Invisible for the hand skeleton's lines and joint dots — fatal for a targeting reticle that must read as circular and for dense monospace readout text.

Two separate resolutions, because the two elements have different needs:

- **The ring and the tether get their own `<svg>` overlay with a viewBox matching the frame's aspect** (e.g. `0 0 400 300`) and the **default** `preserveAspectRatio`. One viewBox serves both surfaces: `.camera-frame` is `aspect-ratio: 4 / 3` in the deck (`deck.css`) *and* in HUD mode (`hud.css`), and `useHandControl` requests `640×480` — also 4:3 — so `object-fit: cover` crops nothing and normalized landmark coordinates map linearly onto either frame with no letterbox or crop correction. **A future surface with a non-4:3 frame would break that silently**: cover would crop, and every overlay would sit offset from the eye it tracks with nothing failing. Units are square by construction, so circles are circles and no counter-transform exists anywhere to be forgotten. The rejected alternative — reusing the `100 × 100` anisotropic space and compensating with `scale(1, 4/3)` on the tracked group — puts a hardcoded 4/3 in JS that silently distorts everything the moment the CSS `aspect-ratio` changes, and requires every future addition to remember the compensation.
- **The panel is an HTML element, not SVG.** Positioned absolutely over the frame with its transform written per frame by the same rAF loop. SVG text in any coordinate space is the wrong tool for a dense typographic readout: it forgoes real font metrics, `letter-spacing`, tabular figures, and text layout, all of which D9 explicitly depends on — and it would need the isotropy fix on top. As HTML it also reuses the app's existing `--font-mono` and monospace-token styling directly (cf. `.cam-status` in `deck.css`), rather than re-deriving it.

The tether is the seam between the two and belongs in the SVG: it is a line, it needs no text, and it must reach the ring's coordinate system at one end. Its panel-side end is therefore computed from the same panel position the HTML element is given, in frame-normalized coordinates both sides can agree on — that shared normalized position, not one owning the other, is what keeps the two in register.

### D11. Code layout — and the testability constraint that dictates it

**The constraint that decides the split.** `vitest.config.mjs`'s `unit` project globs `src/**/*.test.ts` under `environment: "node"`. There is no DOM and no renderer test setup, so **a component cannot be tested at all** in this project as configured, and a `*.test.tsx` file is not merely unsupported — it is silently never collected, so it passes by not running. Therefore anything that must be verified has to be a **pure function in `src/lib/`**, imported by the component rather than living inside it. This is exactly why `src/lib/hand.ts` exists alongside `useHandControl` (`smoothPoint`, `semanticEquals`, extracted "so it can be unit-tested without a camera", per its own comment) and why `src/components/DrawingCanvas.echo.test.ts` tests extracted logic rather than a rendered component. Extraction here is the difference between tested and untested, not a tidiness preference.

**The files, and the precedent each follows:**

| File | Contents | Precedent |
| --- | --- | --- |

| `scripts/vendor-runtime-assets.mjs` | `vendorFaceModel()` | `vendorGestureModel()` |

**Why the rendering is two component files rather than added to `CameraDock.tsx`.** `HandSkeleton` living inside `CameraDock` is fine at 147 lines total, but this capability's two overlays are substantially larger than the skeleton — an eight-layer ring stack with a gradient arc, plus a multi-row readout — and folding both in would push one file well past the 250–450 line convention while giving it three unrelated responsibilities (video preview chrome, hand skeleton, eye HUD). `HandReticles.tsx` already establishes that an overlay does not have to live in the component that conceptually owns it. `CameraDock` stays the composition point.

**Why `eye.ts` and `eye-hud.ts` are separate.** Tracking-domain logic (what the landmarks mean) and presentation math (where to draw an arc) are different responsibilities with different reasons to change, and separating them keeps each test file about one thing. Both are expected to land small — if `eye-hud.ts` approaches the top of the size band, the acquire easing is the natural thing to split off next, since it is the one piece that reasons about time rather than geometry.

**Test-file naming and placement:** colocated `*.test.ts` beside the source file, no `__tests__` directory — the convention throughout `src/lib/` and `src/hooks/`. Extension `.test.ts`, never `.test.tsx`, per the glob above.

### D12. Both surfaces, and the HUD's camera frame grows 30%

**Two camera previews exist, not one.** `CameraDock` renders the deck's; `HudCamera` (a local component inside `HudShell.tsx`, lines 30–66) renders HUD mode's. They are near-identical — same `.camera-frame` markup, same `srcObject = stream`, same `.cam-scan`/`.cam-status`/`.gesture-chip` children — and `HudShell` **already imports `HandSkeleton` from `CameraDock`** to overlay the hand skeleton in both. That import is the precedent this capability follows exactly: `EyeReticle` and `EyeReadout` are imported into both surfaces the same way, and nothing about them is surface-specific.

This is what makes D3's stream-based hook the right shape rather than a refinement: with the hook at `App` level, adding the second surface costs two JSX mounts and no new tracking state.

**HUD mode gets a camera-zoom toggle: normal, or +30%.** HUD mode is the surface that is on screen during a livestream, where a bigger face reads better to an audience than a small corner thumbnail. But HUD mode is *also* the working surface — the overlay the user keeps up while using other applications — and there a larger camera costs desk space that other content needs. Neither size is right all the time, so the size is a **control, not a constant**: a button toggles `.hud-camera` between its current size and ~30% larger (300px → 390px wide at 4:3, i.e. 225px → ~293px tall).

**Default is the current size, and the toggle persists.** Enlarging is the deliberate act, so a freshly-entered HUD looks exactly as it does today and nothing changes for a user who never presses the button. The choice is remembered across sessions via `localStorage`, following the renderer's existing preference pattern exactly — a `*_STORAGE_KEY` constant, a `load…()` initializer used as the `useState` seed, and a write on toggle, which is how `handControl` (`HAND_STORAGE_KEY`), sounds, WebGL quality, and ambient capture are all already stored in `App.tsx`. A streamer sets the frame once and it stays set.

The deck's frame is untouched and has no such control; nothing about the deck is a broadcast surface.

**Widen the camera, not the column.** `.hud-camera` sits in `.hud-left`, which is `width: 300px` and also contains the comms toggle and comms bubbles. Bumping `.hud-left` to 390px is the one-line version and is wrong: it widens the comms panel by 30% too, a visible change to an element nobody asked to change. Instead `.hud-camera` carries its own width, overflowing its column to the right — safe because `.hud-left` is `position: absolute; left: 22px; bottom: 24px` with no `overflow` clipping, so the extra width simply extends rightward into empty overlay space. Express both sizes as CSS custom properties rather than bare literals, so the enlarged factor is one edit point when it is re-tuned against a real stream layout.

**The button follows `.hud-comms-toggle`.** That is the existing precedent for a small labeled pill control attached to a `.hud-left` island, and like every interactive HUD element the new button must carry **`.hud-hit`** — HUD mode is click-through by default, and a control without that class is invisible to the pointer. Placing the button as a sibling *above* the camera in the flex column also means it keeps `.hud-left`'s 300px width regardless of the camera's state, so it does not move when the frame resizes.

**Animating the resize is safe here, unlike D8's case.** The frame's width is set by CSS and is never written per frame, so a `transition` on it does not fight anything: the overlays inside are positioned in normalized/viewBox coordinates, so they scale with the frame automatically and smoothly. This is the distinction D8 turns on — a CSS transition is wrong on a property under imperative per-frame control, and fine on one that is not.

**Voice control of this toggle is deliberately out of scope.** `voice-ui-control` exposes a *fixed vocabulary* of UI actions (readers, history, task-step timelines); adding camera zoom to it would modify that capability's contract for a control the user asked to have as a button. If it is wanted later, it is its own change.

**Two consequences of the size difference worth knowing before building:**

- **The reticle needs no per-surface adjustment.** Its size derives from the iris radius in *normalized* (frame-relative) coordinates times the boost multiplier, so it scales with whatever frame it is drawn in automatically. A single boost value is correct in both surfaces.
- **The readout does not scale, and that is the real risk.** Its type is set in px (following `.cam-status`'s 8.5px), so it occupies a *larger fraction* of a small frame than of a large one, while the offset that places it (D9) is frame-relative — meaning how much of it the frame's left edge clips varies by state. With the zoom toggle there are now **three** states to check by eye — deck, HUD normal, HUD enlarged — not two. If no single value serves all three, scale the panel with the frame; do not vary its content or its offset per state.

## Risks / Trade-offs

- **[Risk] Every visual constant here (ring radii, boost multiplier, tick counts, panel offset, rotation periods) is an unvalidated first guess — none has been checked against a real face at real webcam scale, let alone across face sizes, distances, lighting, or camera quality.** The boost multiplier and the panel offset are the two most likely to be wrong on first run, since both depend on the apparent iris size a given camera actually produces. → Mitigation: the spec constrains legibility and correctness properties (visibly larger than the iris; adjacent layers counter-rotate; periods pairwise distinct and non-harmonic; every rotating layer visibly interrupted; a static reference present; a partial arc doesn't wobble), not exact pixel values — so a clean re-implementation should re-tune the geometry by eye against its own test setup while holding those relationships fixed.
- **[Risk] Running two MediaPipe Tasks Vision inference loops concurrently (GestureRecognizer + FaceLandmarker) against the same video stream is unmeasured — assumed workable because both request the GPU delegate and neither mutates the frame, but not demonstrated, and hand tracking is a functional input device that this decorative overlay must not degrade.** → Mitigation: measure it as an explicit verification task rather than assuming it (does the hand pointer stay as responsive with the eye HUD on as off?); if there is contention, the lever is throttling `FaceLandmarker`'s detection to every Nth frame (cosmetic tracking tolerates more latency than the hand pointer does) rather than reducing hand-tracking fidelity.
- **[Risk] The placeholder panel's fake stats could be mistaken for real telemetry by a user glancing at the screen**, since it's styled convincingly (glowing monospace, a scan-line sweep). → Mitigation: this is explicitly a spec requirement (placeholder-only, not presented as real) — the implementation should keep the content legible as illustrative rather than polishing it into something indistinguishable from a real reading. The churn requirement (D9) helps here rather than hurting: values visibly cycling are self-evidently not measurements.
- **[Risk] The eye-to-element assignment (right eye → ring, left eye → panel) is easy to accidentally flip during a rewrite**, which the spec forbids doing inconsistently. → Mitigation: called out explicitly as its own requirement with a dedicated scenario, specifically because it's the kind of detail a rewrite is likely to consider unimportant and change without noticing. Stated in both landmark and on-screen-side terms (D5) — and the first implementation did in fact get the mirroring backwards, so the on-screen side is the binding one and the landmark index follows from it, never the reverse.
- **[Risk] Splitting the panel (HTML) from its tether (SVG) puts two independently-composited elements in a relationship the eye checks precisely** — a tether that lands a couple of pixels off the panel's edge is more noticeable than either element being slightly misplaced on its own. → Mitigation: D10's rule that both derive from one shared frame-normalized position each frame, rather than one being measured off the other; if sub-pixel register still shows, the tether's terminating tick can be lengthened so its overlap with the panel edge absorbs the error, which is also closer to the reference's look.
- **[Risk] The enlarged HUD frame (D12) is sized for a livestream layout that cannot be checked from inside the app** — 30% is a guess at what reads well to an audience, and the right value depends on the streaming scene's own scale and framing, which only the user can judge. → Mitigation: it is a toggle rather than a constant, so a wrong value is recoverable by pressing the button rather than by shipping a fix; the factor is a single CSS custom property, so re-tuning is one edit; and the reticle scales with the frame automatically, so changing it does not invalidate the ring's tuning.
- **[Risk] The readout's px-set size interacts badly with a frame the user can resize at will** — the deck/HUD size difference (below) is a fixed pair that can be tuned once, but the zoom toggle means the *same* surface now has two frame sizes, so the panel must be checked at both, and a value tuned while zoomed can read wrong the moment the user zooms out. → Mitigation: verify the readout in all three states (deck, HUD normal, HUD enlarged) as an explicit task; if no single value serves them, scale the panel with the frame rather than adding per-state content rules.
- **[Risk] The zoom toggle is a new persisted preference, and a persisted preference that fails to load is silently sticky** — a user who enlarged the frame once and cannot get it back would have no way to diagnose it. → Mitigation: seed it exactly as the existing `localStorage`-backed preferences in `App.tsx` do (a `load…()` initializer that treats an absent or unparseable value as the default), so the failure mode is "reverts to normal size", never "stuck enlarged".
- **[Risk] The panel is clipped at the frame's left edge by design (D9), and a future reader will see that as a bug to fix** — the obvious fix is the edge-flip that was already tried and removed. → Mitigation: the spec states the clipping as the requirement and gives the reason (the flipped position is the ring eye's half of the frame, and any pose-dependent relocation reads as a malfunction); D9 records that it was built and reverted, so the option is closed rather than merely unmentioned. What remains worth checking by eye is how much of the panel is actually lost at a realistic frame edge — if it is most of it, the answer is a narrower panel or a smaller offset, never a relocation.
