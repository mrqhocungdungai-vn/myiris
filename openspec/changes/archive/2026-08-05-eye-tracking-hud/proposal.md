## Why

Iris's Camera/Gesture dock already runs MediaPipe Tasks Vision for hand gestures. `FaceLandmarker` — which yields iris position and size — is a **sibling task in that same installed package**, sharing the same `FilesetResolver` and WASM fileset. So decorative eye tracking needs no new dependency, no second camera session, and no feasibility spike: the capability is a rendering and layout problem, not an integration one.

What this change is for is therefore the design, not the plumbing. The reference is an Iron Man / J.A.R.V.I.S. targeting HUD, and most of what makes that read correctly is **non-obvious from any screenshot of it** — which rotations counter-rotate against which, why the rings are interrupted rather than solid, why the readout is tethered, why its numbers must churn. Those properties are individually easy to build past without noticing, and each one lost degrades the result to generic sci-fi chrome. This proposal pins them down as requirements, alongside three concrete pitfalls in this codebase's existing overlay conventions that a straightforward implementation walks directly into.

## What Changes

- **New capability: decorative iris tracking in the Camera/Gesture dock.** A `useEyeTracking` hook (mirroring `useHandControl`'s shape) runs MediaPipe `FaceLandmarker` over the same camera stream/`<video>` element `useHandControl` already opens — no second `getUserMedia` call — and publishes each eye's live center and radius.
- **Asymmetric per-eye rendering, not a ring per eye.** The two eyes get deliberately different treatments. One eye — the subject's right, appearing on the **right** of the mirrored preview — drives a multi-layer Iron-Man-style "lock-on" reticle tracked at its live position — static wing brackets, a graduated tick dial and solid bezel as the fixed anchor, three counter-rotating full-circle rings, a sweeping accent arc, and a center crosshair — oversized relative to the true iris so it reads on a typical webcam frame. The other (on the **left** of the preview) carries a placeholder telemetry readout beside itself. The preview is mirrored, so on-screen side and anatomical label agree; the spec records the on-screen side as the binding one, because that is the vocabulary a landmark index gets translated into wrongly.
- **The readout is a tethered callout, not a card.** An implied frame (corner brackets, one chamfered corner, no closed outline, translucent so the scene shows through), joined to its eye by an elbow tether whose *both* ends move every frame, with continuously churning values in a layout immune to that churn (right-aligned tabular figures), a segmented — not smoothly filled — meter, and cyan against the reticle's coral/amber so the palette says which element alerts and which reports. It hangs to the frame's left, outward from its eye, and stays there unconditionally — clipped by the frame's left edge rather than relocated, because the only other place to put it is the ring eye's half of the frame, and because a readout that jumps as the head turns reads as broken however carefully the jump is debounced. "An angular panel with cut corners" — the obvious reading of the brief — lands on a styled UI card; each of these is what separates that from the reference.
- **Three motion laws are what produce that look, and none of them are obvious from a screenshot.** Every rotating layer needs an asymmetric interruption (a uniform circle's rotation is imperceptible); *adjacent* layers must counter-rotate (the shear is only legible between neighbours); and periods must be pairwise distinct and non-harmonic (harmonic periods re-sync, and at each re-sync the stack reads as one rigid spinning image). The spec states these as requirements rather than leaving them implicit in a table of tuned constants, because they are exactly what a rebuild loses while still matching every number.
- **A face newly entering frame is *acquired*, not toggled on** — the reticle converges from a larger scale and settles, over a few hundred milliseconds. Appearing instantly at full size on the first tracked frame reads as a sprite switching on, which is where a presence-gated overlay lands by default.
- **Both surfaces, not just the deck.** The overlays render wherever a camera preview appears — the deck's camera dock *and* the glass HUD's. The tracking hook takes the shared `MediaStream` and owns a detached `<video>` (copying `useHandControl`'s own structure) rather than attaching to either surface's video element, so it lives once at `App` level, is surface-agnostic, and **survives a deck↔HUD switch without re-initializing `FaceLandmarker`** — which attaching to a component's ref would force on every mode toggle, since the two surfaces are mutually exclusive and unmount each other.
- **HUD mode gets a camera-zoom button: normal, or +30%** (300px → 390px wide at 4:3). HUD mode is both the livestream surface — where a bigger face reads better to an audience than a small corner thumbnail — and the working surface, where a large camera costs space other content needs. Neither size is right all the time, so the size is a control, not a constant. It **defaults to today's size** (so nothing changes for a user who never presses it) and **persists in `localStorage`**, following the renderer's existing preference pattern (`HAND_STORAGE_KEY` and friends in `App.tsx`). `.hud-camera` carries its own width rather than widening `.hud-left`, whose 300px is shared with the comms panel — the one-line version of this change would silently widen comms by 30% too. The reticle scales with the frame automatically (normalized coordinates), so no ring re-tuning follows; the readout's px-set type does not, so it must be checked in all three states (deck, HUD normal, HUD enlarged).
- **Purely decorative.** Eye position drives only where these two elements are drawn — no gesture, no interaction, no other app behavior derives from it. On/off is the existing hand-gesture toggle; there is no separate switch.
- **A defect in the existing overlay pattern, caught while writing this up.** `HandSkeleton`'s overlay is `viewBox="0 0 100 100"` + `preserveAspectRatio="none"` inside a `4 / 3` frame — an *anisotropic* space where one x-unit is 4/3 the pixels of one y-unit. Harmless for a skeleton of lines and joint dots; fatal for this capability, where it would render every ring as a 33%-stretched ellipse and every glyph 33% too wide. So the reticle and tether get their own SVG with an aspect-matched viewBox (square units by construction, no counter-transform to forget), and the readout is plain HTML — SVG text forgoes the font metrics and tabular figures its layout depends on.
- **A reusable pitfall worth codifying — declarative CSS on an imperatively-driven transform.** Two instances: (1) CSS `transform-box: fill-box; transform-origin: center` only rotates correctly around an element's true center when that element's own bounding box is centered there — true for a full circle at the local origin, **false** for a partial arc, whose bounding box spans only the swept wedge, so the accent arc orbits its own centroid instead of spinning in place. Fix: an imperative per-frame SVG `rotate()`. (2) The acquire animation cannot be a CSS transition on the ring group's transform, because the rAF loop rewrites that transform every frame and cancels it — it has to be folded into the per-frame write as an eased scale factor. The spec states both, so a fresh implementation doesn't reintroduce either.
- Vendors one new model asset, `face_landmarker.task`, alongside the existing `gesture_recognizer.task`, following the same downloaded-once-and-cached pattern in `scripts/vendor-runtime-assets.mjs`.

## Capabilities

### New Capabilities

- `eye-tracking-hud`: decorative MediaPipe-`FaceLandmarker`-based iris tracking in the Camera/Gesture dock — shared camera session, asymmetric per-eye rendering (a lock-on ring HUD at one eye, a placeholder telemetry card beside the other), no interaction derived from it, and the partial-arc rotation pitfall as a stated constraint.

### Modified Capabilities

- `glass-hud-mode`: its spec enumerates what HUD mode presents, naming "the camera dock with hand skeleton" — this change adds the eye overlays to that surface **and adds a new HUD control** (the camera-zoom toggle, with its own persisted preference), so that requirement needs updating. The zoom toggle is `glass-hud-mode`'s behavior, not this capability's: `eye-tracking-hud` only requires that its overlays scale with whatever frame they are drawn in. This change carries a `specs/glass-hud-mode/spec.md` delta with the modified layout requirement plus a new requirement for the camera-size control.

`two-hand-gestures` (hand tracking, the camera toggle, per-hand reticles) is reused exactly as it stands today — this change adds a sibling overlay to the same previews, it does not change any of that capability's requirements. `renderer-structure`'s component-file requirement is satisfied as written (new components each get their own file under `src/components/`) and needs no change.

## Impact

**Code** — file-by-file placement and its rationale against this repo's conventions is design D11; in summary:

- `src/hooks/useEyeTracking.ts` (new) — the tracking hook, sibling to `useHandControl.ts`.
- `src/lib/eye.ts` + `src/lib/eye.test.ts` (new) — pure eye-state logic, exactly as `lib/hand.ts` relates to `useHandControl`.
- `src/lib/eye-hud.ts` + `src/lib/eye-hud.test.ts` (new) — pure presentation math: ring geometry and the readout's hysteretic side-selection.
- `src/components/EyeReticle.tsx` (new) — the SVG overlay: ring stack + tether, in its own aspect-matched viewBox.
- `src/components/EyeReadout.tsx` (new) — the HTML readout panel, following `HandReticles.tsx`'s existing per-frame-transform overlay pattern.
- `src/components/CameraDock.tsx` — mounts those two overlays; nothing else. `HandSkeleton` stays as it is.
- `src/components/HudShell.tsx` — `HudCamera` gains the same two mounts, as it already does for `HandSkeleton`.
- `src/App.tsx` — calls `useEyeTracking(handStream, handControl)` beside `useHandControl` and threads `{ eye, eyeRef }` to both surfaces, exactly as `hand`/`liveHandRef` already reach both.
- `src/styles/hud.css` — `.hud-camera`'s two widths as CSS custom properties, and the zoom button's styling (following `.hud-comms-toggle`).
- `src/App.tsx` (also) — the zoom preference: a `*_STORAGE_KEY` constant, a `load…()` `useState` seed, and a write on toggle, exactly as the existing `localStorage`-backed UI preferences do.
- `src/styles/claude.css` — all new HUD-specific rules (`deck.css` and the other upstream-verbatim stylesheets are never touched for Iris-specific styling, per existing convention).
- `scripts/vendor-runtime-assets.mjs` — `vendorFaceModel()` alongside `vendorGestureModel()`.
- `docs/GESTURES.md` — needs a new "Eye HUD (decorative)" section; the file currently mentions eyes nowhere.

**Testability is what drives that split, not tidiness.** `vitest.config.mjs`'s `unit` project globs `src/**/*.test.ts` under `environment: "node"` — there is no DOM and no renderer test setup, so **no component can be tested at all**. Anything that must be verified has to be a pure function in `src/lib/`. That is the whole reason `lib/hand.ts` exists beside `useHandControl`, and this capability follows it.

**Dependencies:** none new — `@mediapipe/tasks-vision` is already installed for hand gestures; `FaceLandmarker` is a sibling task in the same package.

**Risk:** low — additive, decorative, gated behind the existing opt-in camera toggle, degrades to "no rings" on load failure rather than surfacing an error. The one non-decorative addition is HUD mode's camera-size control, which defaults to today's size and so is a no-op for anyone who never presses it.

**Spec deltas:** two — `specs/eye-tracking-hud/spec.md` (the new capability) and `specs/glass-hud-mode/spec.md` (its layout requirement modified for the eye overlays and the size control, plus a new requirement for that control's behavior and persistence).
