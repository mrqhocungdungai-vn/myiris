## Context

Iris's voice loop runs on a Gemini Live session configured once in `buildLiveConfig()`
(`electron/main.mjs:3018`). Today that configuration relies on the server's automatic activity
detection (AAD): Gemini decides when the user has stopped speaking and commits a turn. That is
correct for conversation and wrong for monologue — every pause is read as an invitation, so Iris
answers into gaps that were not questions.

The two existing controls do not cover this. Speaker mute (`openspec/specs/speaker-mute/spec.md`)
suppresses playback but leaves Gemini generating turns that still enter conversation history.
Microphone mute stops the interruptions by making Iris deaf.

**Every mechanism decision below was measured against the live API before being written down; the Risks
section marks what was not.** The spikes are kept
in **[`spikes/`](spikes/)** — four `spike-listen*.mjs` and three `probe-*.mjs` — with
`spikes/README.md` mapping each one to the decision it established and `spikes/make-clips.sh`
regenerating its audio. They connect real sessions with `@google/genai` 2.10, stream Vietnamese
speech generated by macOS `say -v Linh` converted with `afconvert` to 16 kHz mono PCM, and assert on
what comes back. They are not part of `npm test` — they need `GEMINI_API_KEY` and the network, which
`docs/TESTING.md` forbids in the suite.

Two of those spikes encoded designs that read correctly from the SDK documentation and **do not
work**; both are recorded under Decisions so nobody rebuilds them.

## Goals / Non-Goals

**Goals:**
- Iris hears and retains everything during a 10–20 minute monologue and cannot speak during it.
- That silence is a property of the session configuration, not a prompt asking politely.
- When the user ends the mode, Iris synthesizes what it heard, and ordinary conversation continues
  with the memory intact.
- Normal conversation is byte-for-byte unchanged when the mode is off.
- Reuse what exists — the speaker-mute control shape, the resumption handle, the microphone pipeline.

**Non-Goals:**
- System-audio / loopback capture, and any meeting-capture role. Iris deliberately does not own that
  audio layer; a separate integration (e.g. meetily) is the future answer, and this change must not
  grow a capture stack that would have to be unpicked later.
- Detecting the bare word "iris" spoken mid-sentence as a trigger. The bundled wake-word model is
  `public/wakeword/hey_iris.onnx`, an openWakeWord model trained for the exact phrase "Hey Iris"; it
  cannot fire on "Iris nghĩ gì về vấn đề này". Supporting that needs a newly trained model, and a bare
  two-syllable name carries a far higher false-positive rate — out of scope here.
- Reacting to the wake word during the mode at all. The wake-word listener is active only while the
  app is asleep (`openspec/specs/wake-sleep-voice/spec.md:9`), so "Hey Iris" mid-monologue already
  does nothing. Stated so that "let the user interrupt by voice" is not read as a gap to fill.
- Writing session transcripts, audio, or summaries to disk, to `~/iris-second-brain`, or anywhere
  outside process memory.
- Any new control for "stop listening" or "stop talking". Microphone mute and speaker mute already
  are those controls.
- An "ask now without leaving the mode" affordance. Shown to be possible (see Decision 11) but not built.
- A new orb state. Verified non-issue: `audio_state` stays `"listening"` (`electron/main.mjs:3117`)
  so `reactorState` already resolves to `"listening"` (`src/App.tsx:648`), and the thinking swirl
  self-clears after 6 s (`src/App.tsx:381`) rather than latching for the whole mode. Rotation
  boundaries do not disturb it either, because Decision 6 suppresses them before the speaking state is
  emitted. The ear control is the only new visual feedback, so `orb-expressions` stays untouched.
- Anything touching power management. `powerMonitor` and `powerSaveBlocker` appear nowhere in the app
  today, and Decision 10 removes the reason to introduce them: a sleep long enough to drop the
  connection ends the mode, so the rotation timer's behavior across suspension is not load-bearing.
  Keeping the machine awake for a listening session would be a heavyweight, user-hostile change for a
  control meant to be peer to speaker mute.
- Any `main-thread-budget` work. Verified: every requirement in that spec concerns the *renderer's*
  main thread (orb `useFrame` allocation, `AudioWorklet` over `ScriptProcessorNode`, no sync modals),
  while the rotation timer and boundary sequence are main-process Node work. There is also no local
  energy delta to manage: the renderer already streams 16 kHz PCM continuously in ordinary
  conversation, and `backgroundThrottling: false` is already set (`electron/main.mjs:3329`), so
  occlusion changes nothing. This mode's extra cost is server-side tokens.
- Repairing the pre-existing deadness of the mute and sleep tray items after a window close (both go
  through `emitToRenderer`, `electron/main.mjs:3433` and `:3428`). Decision 11 keeps the *new* surfaces
  out of that trap; fixing the old ones belongs to `speaker-mute` and `wake-sleep-voice`.
- Anything about the Glass HUD morph. Verified non-issue: `enterHud`/`exitHud`
  (`electron/main.mjs:3367`) only resize and restyle the existing window — no reload, no navigation,
  same renderer and same `AudioContext` — so morphing while engaged needs no handling. Stated so it is
  not re-investigated.

## Decisions

### 1. Reuse the Gemini Live session with AAD disabled, rather than a separate transcription path

**Decision:** listening mode is the same Live session under a different `realtimeInputConfig`:
`automaticActivityDetection: { disabled: true }`, `turnCoverage: "TURN_INCLUDES_ALL_INPUT"`,
`activityHandling: "NO_INTERRUPTION"`.

Alternatives considered and rejected:
- *A separate cloud STT channel* (buffer PCM, chunk it to `generateContent`, keep Live disconnected
  while listening). Guarantees silence trivially, but throws away the thing that makes the feature
  worth having: Gemini keeps the **audio** in context, including hesitation and emphasis, not a
  flattened transcript. It also duplicates a transcription path the Live session already provides for
  free via `inputAudioTranscription`, already enabled at `electron/main.mjs:3035`.
- *On-device STT (whisper.cpp)*. Adds a native dependency to bundle and sign, spends CPU for the
  whole session against the `main-thread-budget` capability's intent, and puts Vietnamese technical
  speech accuracy on the critical path.
- *Raising `silenceDurationMs`* on `AutomaticActivityDetection` so Iris waits longer before deciding
  the user finished. This is the closest thing to a built-in "pause tolerance" knob, and it is the
  wrong tool: it only *delays* the interruption. Stay quiet long enough and Iris speaks anyway. It is
  also per-session configuration, so it does not avoid the reconnect that Decision 12 accepts.

### 2. Silence comes from an unclosed activity, not from `sendClientContent`

**This is the first decision a spike got wrong, and it is one of the two most important to record.**

Reading the SDK, `sendClientContent({turnComplete: true})` looks like the mechanism: its
documentation names the use case "Managing turns when not using audio input and voice activity
detection" (`genai.d.ts:11446`), and `turnComplete` is described as starting generation "with the
currently accumulated prompt" (`genai.d.ts:8660`). The natural reading is that streamed realtime
audio accumulates and `sendClientContent` commits it.

**It does not.** With `automaticActivityDetection.disabled: true` and no `activityStart` ever sent,
the server discards the audio entirely. Measured: after streaming 11.4 s of speech,
`inputTranscription` was empty and the model replied *"Rất tiếc, tôi không nghe được những gì bạn vừa
trình bày."* Audio streamed outside an explicitly opened activity does not exist as far as the model
is concerned.

**Decision:** with AAD disabled, audio only counts as user input inside an activity opened by
`sendRealtimeInput({ activityStart: {} })`. While an activity is open no turn can complete, which is
why Iris is silent. Measured across four separate sessions: activity open, speech streamed, zero
audio chunks and zero `turnComplete` messages. Silence is structural, not prompted.

### 3. The connection lifetime forces the monologue into chunks — one activity cannot span it

**Decision:** listening mode is a sequence of chunks, not one long activity. Each chunk is
`activityStart` → stream → boundary → reconnect → `activityStart`.

Gemini Live closes each WebSocket connection after roughly ten minutes; this is already documented
and handled in the codebase (`electron/main.mjs:87`, `goAway` at `:3206`, `onclose` →
`scheduleReconnect` at `:3141`). A design holding one activity open across a 10–20 minute monologue
therefore guarantees the connection dies mid-activity — and by Decision 4 an activity that is never
closed is never committed, so the whole monologue evaporates while the auto-reconnect succeeds and
Iris looks fine.

**Rotation is driven by our own timer with margin, not by racing the server's `goAway`.**
`IRIS_LISTEN_CHUNK_MS` (default 8 minutes) triggers a boundary; a `goAway` arriving earlier triggers
one immediately. The reason for the margin rather than waiting for `goAway`: `goAway.timeLeft` has
**not** been measured (see Risks), and a boundary takes ~2.5 s, so a design that only reacts to
`goAway` bets the entire chunk on an unmeasured server value. Rotating early costs one extra
reconnect and removes the bet.

Chunk boundaries are invisible to the user: by Decision 6 the forced turn is neither played nor
rendered.

### 4. A boundary is the only way to commit — so exiting must let Iris speak

**Measured: closing the session without sending `activityEnd` loses the entire listening context.**
The reconnected conversation session answered *"tôi không có thông tin về điều bạn vừa nói trước
đó."* `activityEnd` is simultaneously the commit and the trigger for a model turn; there is no way to
have one without the other.

Therefore exiting listening mode is just the *last* boundary, and **Iris speaks its synthesis**. This
must be documented as forced, because to a future reader it looks like a gratuitous decision to make
the app talk when the user only asked it to stop listening. Any future change that wants a silent
exit must first establish another way to commit the context.

**The exit boundary is byte-for-byte a rotation, including suppressing its turn.** The only difference
is which configuration is reconnected into — converse rather than listen again — and that the synthesis
turn is driven afterwards, in the conversation session.

Driving the synthesis *at* the boundary is the tempting shortcut and it does not work. At that moment
the session still carries the listening system instruction, which Decision 6 requires to ask for the
briefest possible reply; the spiked version says literally *"chỉ được trả lời đúng một từ: ok"*. Nothing
distinguishes the final boundary from a rotation for the model, so a synthesis requested there gets the
same `ok`. This is exactly how the working spike does it: `spike-listen4.mjs` reconnects into converse
with the conversation instruction and *then* asks its question, and that is the run whose synthesis
merged all three chunks. Driving it after the reconnect also makes the synthesis an ordinary turn, so
speaker mute, barge-in, and transcript rendering need no special handling.

Both the entry confirmation and the synthesis SHALL be driven with
`sendClientContent({ turns, turnComplete: true })`, which is the measured-working way to drive a turn —
not `sendRealtimeInput({ text })`. The latter is what `sendWelcomeGreeting` (`electron/main.mjs:3075`)
uses and is therefore the natural thing to copy, but its behavior under AAD-off is precisely what
Decision 8 flags as unmeasured and possibly discarded; a discarded confirmation means the user gets no
feedback that the mode engaged at all.

### 5. No resumption checkpoint exists while an activity is open — the boundary must wait for the handle

**This is the second decision a spike got wrong, and the subtler of the two.**

Measured (`probe-handle.mjs`): with an activity held open for 160 seconds, the server emitted
**zero** `sessionResumptionUpdate` messages. Measured (`probe-handle2.mjs`): after `activityEnd`, a
`resumable=true` handle arrived **0.6 s after** `turnComplete`. This matches the SDK's own warning
that resumption is impossible at some points, "example of such case could be model executing
function calls or just generating" (`genai.d.ts:8792`).

Two consequences, both load-bearing:

- **The boundary must await the handle before closing the session**, not close at `turnComplete`.
  `spike-listen4.mjs` first closed immediately after the turn, received no handle, and the final
  answer was *"Bạn chưa cung cấp thông tin nào"* — a total context loss that looked exactly like a
  broken design. Adding a wait for the resumable handle turned every assertion green. `turnComplete`
  looks like the natural end of the sequence, so an implementer will make this mistake.
- **The session must never be allowed to close with an activity open.** There is no fresh handle in
  that state, so resumption falls back to a checkpoint from before the mode was entered and the
  current chunk is unrecoverable. This is what motivates the timer margin in Decision 3, and it is
  not hypothetical: `probe-goaway.mjs` had its session terminated at 241 s by
  `Resource has been exhausted (e.g. check quota)` with the activity still open.

Full boundary sequence, in this order: `activityEnd` → await `turnComplete` → **await a
`resumable=true` handle issued *after* that `activityEnd`** → close → reconnect carrying that handle →
`activityStart` (rotation only).

The freshness qualifier is not pedantry. `main.mjs` keeps the handle in a module-scoped variable
assigned on any resumable update (`:3201`), so entering listening mode inherits a non-null handle from
the converse session. An implementation that waits for "a handle" therefore satisfies the condition
instantly and closes right after `turnComplete` — reproducing the exact failure while appearing to
implement its fix, and passing a test that only checks "a handle was present". The spikes escape this
only because each connection gets a fresh sink; `probe-goaway.mjs` does not, and can report success off
a pre-monologue checkpoint.

Measured end to end (`spike-listen4.mjs`): three chunks with a reconnect at every boundary, then a
converse reconnect. A question answerable only from chunk 1 was answered correctly, and a summary
request merged specifics from all three chunks. (Only the chunk-1 recall reproduced on both runs; the
merged-summary check is question-dependent and is recorded as informational in `spikes/README.md`.)

### 6. Rotation-boundary turns are committed but neither spoken nor rendered

A rotation boundary forces a model turn that the user did not ask for. Playing it would interrupt the
monologue — the one thing the mode exists to prevent — so its audio is dropped and its text is not
surfaced as a transcript line.

**Suppression belongs in the main process, not in the renderer's speaker-mute path.** Reusing speaker
mute looks like the frugal option and does not work: `main.mjs` appends the turn's text to
`modelTranscriptBuffer` (`:3231`) and emits it as a `transcript` event at `turnComplete` (`:3241`),
and it emits `audio_state: "speaking"` per audio chunk (`:3238`) — both before the renderer sees
anything. A rotation would therefore still print a transcript line and visibly flip the orb even with
every audio frame discarded downstream. Skipping the `modelTurn` loop and the `outputTranscription`
append while a rotation boundary is in flight is both correct and less code: nothing crosses IPC, so
there is nothing to suppress on the far side, and the behavior no longer depends on the renderer being
alive or on what the user has muted.

This is also what keeps the "no new orb state" claim true: the orb needs no listening variant because
a rotation never reports speaking in the first place.

**The listening configuration also carries an empty tool set.** `buildLiveConfig` ships
`...buildClaudeTools()` (`electron/main.mjs:3046`), and `handleLiveMessage` dispatches
`message.toolCall` (`:3212`) before it touches `serverContent` — so suppressing audio and transcript
text would hide a boundary turn's *speech* while still letting it start a real Claude run the user
never asked for. The spikes could not have caught this: their configs declare no tools at all, so
"the reply was `ok` every time" does not transfer to production. Emptying the tool set costs nothing,
because Decision 12's risk list already establishes that no tool call can work during a chunk anyway.

The turn is also made cheap by prompt: the listen-mode
system instruction tells Iris to answer a boundary with exactly one word. Measured across three
boundaries, the reply was `"ok"` every time — one token. The `activityEnd`-to-`turnComplete` latency was
~1.7 s, timed by `probe-handle2.mjs` (the only spike that timestamps the sequence).
This is a cost optimisation only; silence during the chunk remains structural per Decision 2, and
a prompt that failed to produce `"ok"` would waste tokens, not break the mode.

### 7. Segment records are kept in memory, with exactly two consumers

`inputAudioTranscription` is already enabled (`electron/main.mjs:3035`), so each chunk's transcript
arrives for free. **Decision:** accumulate it per chunk in memory for the life of the listening
session.

This reverses an earlier decision in this change, and the reason is Decision 5, not preference. The
earlier reasoning was that the resumption handle preserves memory across the config change, so no
transcript was needed — true, and still true, but it assumed a single activity and a single clean
reconnect. Once the connection can die mid-chunk with no checkpoint available, the in-memory
transcript is the *only* record of the current chunk. It is a recovery path, not a duplicate of the
model's context.

Alternative rejected: having Gemini summarise each chunk at its boundary instead of keeping the
transcript. That turns every boundary into a real analysis turn — seconds of latency and real token
cost every 8 minutes — and if a summary is wrong, the wrong summary is all that survives. The final
synthesis is better done once, with all chunks' audio in context, than assembled from partial
summaries.

**Its consumers must be named, or the record becomes a store looking for a use.** Decision 10 made an
unexpected disconnect *end* the mode, which removed the consumer this decision was originally written
for — a later synthesis in a still-running listening session. The two that remain:

1. The closing synthesis, when a boundary's bounded wait elapsed so the chunk may not have committed.
2. The synthesis Decision 10 produces after an unexpected disconnect, where the model's context is
   missing everything since the last successful boundary. This is the case that keeps a slept-machine
   or dropped-network session from vanishing without a word.

Scope limits, stated so they are not quietly exceeded: memory only, never written to disk or the notes
vault; discarded once the closing synthesis has been delivered; no consumer beyond the two above
without a stated reason. Note the transcript is normalised, not verbatim — measured, `"ba giờ"` came
back as `"3:00 chiều"` — so nothing may depend on exact wording.

### 8. Announcements are deferred while the mode is engaged

`notifyIris` (`electron/main.mjs:720`) sends `sendRealtimeInput({ text })` whenever `liveSession` is
truthy and buffers only when it is null. While the mode is engaged the session *is* connected, so
every announcement — task completion, role selection, workspace change — would be injected as text
into the session that must stay silent. Text realtime input is not gated by activity detection, so it
either completes a turn and Iris interrupts the monologue, or the server discards it and the
announcement is lost in violation of `session-announcements`. Neither was measured; both are bad.
`drainPendingAnnouncements()` also runs on **every** connect (`electron/main.mjs:3147`), so a
rotation reconnect would dump the whole backlog into a listening session.

**Decision:** while engaged, an announcement takes the buffer path, and the drain is skipped on a
listen-config connect and runs after the exit reconnect. This changes `session-announcements`'
stated behavior, so this change carries a MODIFIED delta for it.

### 9. A single spoken confirmation on entry

XX2's reconnect means the first moment after the toggle is exactly when the session is least ready.
Iris therefore speaks one short line on entry, then goes silent.

Sequence: reconnect into listening configuration → drive one turn for the confirmation → wait for it
to complete → `activityStart`. Opening the activity only after the confirmation turn finishes keeps
the confirmation from consuming the user's opening words.

This is the one decision taken on the user's behalf rather than settled explicitly. It is
deliberately the smallest version of what they described, and it is severable — dropping it leaves
the mechanism intact, with the ear control's visual state as the only feedback.

### 10. An unexpected disconnect ends the mode — which is why no power API is needed

**Decision:** if the session closes unexpectedly while engaged, listening mode ends.

macOS sleeping is the ordinary case of this, and the current reconnect path handles it badly by
default. `onclose` with `userStopped` false calls `scheduleReconnect` (`electron/main.mjs:3141`), which
rebuilds the configuration from `buildLiveConfig(resumptionHandle)` (`:3110`) with no notion of a mode.
Both possible behaviors are silent failures: reconnecting in converse configuration leaves the ear
icon lit while Iris resumes interrupting, and reconnecting in listen configuration without an
`activityStart` means every subsequent byte is discarded — and since nothing is retained, the input
transcription stops too, so the segment record silently stops growing as well.

Ending the mode is not the same as losing the session: once converse is restored, Iris speaks a
synthesis drawn from the segment record (Decision 7's second consumer). The user gets what they were
waiting for, from the only account that survived, instead of fifteen minutes of thinking aloud
disappearing in silence.

Ending the mode is the smallest correct answer. The alternative — reopening an activity on the
reconnected session and stitching the chunk back together — is a recovery mechanism for a case the
user can resolve in one click, on a control that is meant to be peer to speaker mute.

The valuable consequence is what this decision makes *unnecessary*: neither `powerMonitor` nor
`powerSaveBlocker` is needed, and whether an 8-minute `setTimeout` fires late or immediately after a
suspend stops mattering, because the mode is already over. Neither API exists in the app today and
neither is introduced here.

### 11. Follow speaker-mute's lifecycle shape, but not its control routing

Ephemeral per session, never persisted, reset on any session teardown including a server-initiated
one; three surfaces with identical effect (renderer control in deck and HUD, tray item whose label
reflects state and is disabled while asleep, global hotkey via `IRIS_LISTEN_HOTKEY`); hotkey
registration failure logged and survivable. Every one of those properties already has a tested
precedent in `openspec/specs/speaker-mute/spec.md`, so imitating it costs nothing and avoids a
second, subtly different lifecycle for a sibling control. Unregistration on quit needs no new code:
`app.on("will-quit", () => globalShortcut.unregisterAll())` at `electron/main.mjs:3778` already
covers any newly registered shortcut.

**Two things about speaker mute must NOT be copied, because ownership is inverted.** Speaker mute is
renderer-owned (only the renderer can drop audio) and main mirrors it, so its tray item and hotkey both
dispatch to the renderer — `emitToRenderer("iris:mute-toggle", {})` at `electron/main.mjs:3747` and
`:3433` — and the renderer reports its value back (`src/App.tsx:488`, whose own comment notes it
"fires on mount (seeds `false`)"). Listening mode is main-owned, so:

- The tray item and hotkey call main's toggle **directly**. `emitToRenderer` returns early when there
  is no window (`electron/main.mjs:213`), the deck's close button calls `mainWindow.close()`
  (`:3712`), and `window-all-closed` deliberately does not quit on darwin (`:3791`). Copying the mute
  routing would therefore produce a mode that is still engaged — session open, activity open, rotation
  timer running — with every control that could end it dead. Calling main directly is also less code.
- There is **no report-back channel**. A renderer that reported state on mount would flip the
  authoritative flag to disengaged after a reload while a chunk was still open. Main pushes state one
  way; the renderer additionally gets a query for boot and reload, matching how `sidecar:status`
  (`:3557`) and `pipeline:status` (`:3724`) are already exposed.

The renderer control is a human-ear icon, crossed out when the mode is off — the mode toggle, and the
only affordance. Per Decision 4 there is no separate "speak now" button: ending the mode is what
permits Iris to speak.

Also measured (`spike-listen3.mjs`): several `activityStart` → `activityEnd` cycles work inside one
session, so an "ask now, stay in listening mode" affordance is achievable. Not built here.

### 12. The mode's reconnect needs its own path, separate from the failure reconnect

`onclose` (`electron/main.mjs:3129`) calls `scheduleReconnect` unless `userStopped` is set, so closing
the session to swap configuration would fire the exponential-backoff failure path racing the
intentional reconnect — and `scheduleReconnect` nulls `resumptionHandle` after three attempts
(`:3167`), destroying exactly the memory this design rests on. Neither existing entry point is
reusable: `startLive` early-returns when `liveSession` is set (`:3079`), and `stopLive` nulls
`resumptionHandle` and sets `userStopped = true` (`:3248`).

**Decision:** a distinct deliberate-transition path that `onclose` honours the way it honours
`userStopped`, without the offline teardown, reconnecting via the existing `{ isReconnect: true }`
route so `GreetGate.arm()` (`:3121`) does not re-fire the welcome greeting on every toggle and every
rotation.

## Risks / Trade-offs

- **`goAway.timeLeft` was never measured.** `probe-goaway.mjs` intended to, but its session was
  terminated at 241 s by a quota error before `goAway` fired. → Decision 3's timer margin is
  specifically so this number is not load-bearing; `goAway` is an early trigger, not the primary one.
  Worth measuring later, but nothing depends on it.
- **An unclean disconnect mid-chunk loses that chunk from the model's context.** Observed once, from
  quota exhaustion. → The in-memory segment record (Decision 7) is the recovery path. Chunks already
  committed are unaffected.
- **Continuous listening consumes quota faster than conversation**, because `ALL_INPUT` counts
  silence toward the turn — roughly 25 audio tokens per second regardless of whether anyone is
  speaking, about three times conversation's rate per wall-clock minute. Twenty minutes is ~30k
  tokens, far below the existing `triggerTokens` of 104857, so `contextWindowCompression` never fires
  at the intended length. A quota ceiling was hit during testing after a day of repeated spikes; it is
  unclear whether that reflects the account's tier or the mode's own draw.
- **The reconnect drops audio, so the user's first words can be lost** — at entry and, more quietly,
  at every rotation boundary. → Decision 9's confirmation covers entry. At a rotation there is no cue,
  so a word spoken exactly across the boundary may be missed; accepted, since the mode is for thinking
  aloud rather than transcribing an event.
- **Iris speaks on exit whether or not the user wanted a synthesis right then.** → Forced by Decision
  4; the alternative is losing the session. Speaker mute remains available.
- **A future reader may "simplify" the sequence** by dropping `activityStart`, replacing `activityEnd`
  with `sendClientContent`, or closing at `turnComplete` instead of waiting for the handle. All three
  produce a mode that appears to work — sessions connect, Iris stays quiet, Iris answers when asked —
  while having heard nothing. → Decisions 2, 4 and 5 record the measured failures, and the specs carry
  scenarios that fail if any of them lands.
- **Voice sleep is unreachable while engaged.** `go_to_sleep` (`openspec/specs/wake-sleep-voice/spec.md:126`)
  is a Gemini tool call, which needs a model turn; no turn can complete during a chunk. The same
  applies to any delegation the user asks for by voice. Hotkey and tray sleep still work, so this is a
  documented surprise rather than a defect.
- **A PO question raised while the mode is engaged cannot be relayed.** The relay's delivery mechanism
  is Gemini reading it aloud (`openspec/specs/voice-decision-relay/spec.md:19`), so an in-flight
  `AskUserQuestion` will hit `IRIS_PO_QUESTION_TIMEOUT_MS` and auto-apply the recommended default
  without the user ever hearing it. → Growing the relay a non-voice path is out of scope for a minor
  control; recorded because the failure is silent.
- **`probePipelineAvailability()` runs on every connect** (`electron/main.mjs:3101`), so every toggle
  and every rotation re-probes the `claude` binary. The "~1–2 s" reconnect estimate may be optimistic.
- **Listening mode gives no signal that microphone capture has stopped.** In ordinary conversation a
  dead mic is obvious within one turn, because Iris stops answering. Here silence is the designed
  behavior, so a mic lost mid-session — device unplugged, or a capture `AudioContext` left suspended
  after a system sleep — yields a silent partial session with zero feedback. The underlying gap is
  pre-existing: `microphone-device-selection/spec.md:59` promises a fallback to System Default, but in
  code that fallback lives only inside `startCapture` (`src/hooks/useAudioPipeline.ts:121`) with no
  `devicechange`-driven restart, and the capture context is never resumed the way the playback one is
  (`useAudioPipeline.ts:246`). → Recorded here because this mode is what makes the gap
  consequence-bearing; fixing it belongs to `microphone-device-selection`, not to this change.
- **Nothing here has been validated outside `npm start` / `npm run dev`.** The app has not been
  packaged, installed, and run over days. The honest listening-mode-specific unknowns are: stability
  across many rotations in a long real session, and the quota draw of continuous `ALL_INPUT` — a
  ceiling was hit once during spiking (see the first risk above), and whether that reflects the
  account's tier or the mode's own consumption is unresolved. → Recorded deliberately as a limitation
  to return to when the app is genuinely installed and used long-term.

  Three risks a reader might expect here were checked and are **not** real for this feature.
  `openspec/` is not bundled: `files` is an explicit allowlist of `dist/**`, `electron/**` minus tests,
  three icons and `package.json` (`package.json:75`), and `extraResources` is only the two `resources/`
  folders (`:84`) — the spikes and their generated audio never enter the app. `Tray` and
  `globalShortcut` need no entitlement and no TCC grant, so signing and notarization do not affect the
  new surfaces; that would only change if someone chose a **media key** accelerator, which needs an
  event tap. And PATH matters only to the `claude` probe, which this mode does not touch.

  The signing risk that *is* real is a different one, and it is pre-existing and app-wide rather than
  this change's: there is no signing configuration at all — no `hardenedRuntime`, no `entitlements`, no
  notarization, and `mac.target` is `["dir"]` (`package.json:94`), so `dist:mac` does not yet produce a
  distributable. Notarization requires hardened runtime, and electron-builder's default entitlements
  template does not include `com.apple.security.device.audio-input`, which is what will break the
  microphone on a first notarized build. Out of scope here; noted so the caveat points at the real
  hazard instead of an invented one.

## Open Questions

- Decision 9's entry confirmation is the only thing decided rather than agreed. If the user wants no
  speech at all on entry, remove it; the mechanism does not depend on it.
- `goAway.timeLeft`'s actual value, and whether the quota ceiling observed during testing is a tier
  limit or a property of continuous listening. Neither gates this change.
- Exact wording of the entry confirmation, the boundary "answer ok" instruction, and Iris's exit
  synthesis prompt is left to implementation, since all three are prompt text rather than behavior.
